# HXBot v1.7.1 · 多开智能体卡死：根因报告（BUG-CONC-01）

**依据：**《需求规格说明书 V2.1》第 5.1 节 BUG-CONC-01 及验收条目 BUG-CONC-01-A1～A4。
**数据：**《并发基线-v1.7.1.json》（同目录）。修复前（V1.7.0，桌面端 0.67.9）与修复后（v1.7.1，桌面端 0.67.10）用同一个压力脚本、在同一台机器上运行。
**审阅：**审阅人：__________　日期：__________　结论：□ 同意　□ 不同意（意见：__________）（BUG-CONC-01-A4 要求另一位审阅人签字）

## 1 结论

用户报告的“多开智能体时界面卡死”有三个可证的原因，都已修好：

1. **调度：V1.7.0 的桌面端没有容量闸。**`src/backend/memory-hold.ts` 在桌面端拿到的内存读数是 null，永远放行；`drain-scheduler.ts` 的上限也是 null。团队成员、对话、定时任务的回合一起开始：压力测试里同时在跑 32 个回合，智能体进程常驻内存 5.5 GB（测试机共 8 GB）。测试机上没有别的应用，内存还够，所以这里主进程没有卡；在开着别的应用的 8 GB 电脑上，再多 5 GB 会把整台电脑推进换页，HXBot 的窗口和别的应用一起卡住（这一步是推断，没有在真机上复现，见第 6 节）。同一时间，团队的分派因为“在忙的人太多”被退回 58%。
2. **持久化：频道列表随历史线性变慢（上游代码）。**`ChannelStore.list` 每次都把读者没读过的频道（例如用户不打开的团队房间）的全部消息逐条解析 JSON 再数未读；侧栏和回复提醒在每个 `channels-changed` 上各读一遍，流式回复每一帧都发 `channels-changed`。30 分钟测试的库（3 MB 消息）每次 10 毫秒，放大到 89 MB 时每次 209 毫秒。用得越久，主进程花在这上面的时间越多，直到事件循环被占满——这正是“用久了、多开时卡死”。
3. **持久化：启动时读整段频道历史（上游代码）。**启动时 `ChannelService.recover` 对每个频道线程做一次整份快照的 `capture`，每次都把整个频道的历史读出来解析。团队房间有十几个成员线程，在 89 MB 的老库上，V1.7.0 启动后主进程卡 26 秒，v1.7.1 改之前卡 49 秒（团队房间更多）。

在老库上，修复前整场 p99 是 612 毫秒（门槛 200），修复后 39 毫秒（第 5 节）。

另有一处 v1.7.1 自己差点引入的问题，修复前就在测试里发现并修掉：排队以后，上游的 `hasAgentAssignmentInState`（对全部历史分派做无索引的 JSON 查询）在每条等着的线路每次检查时都执行，30 分钟里卡顿从 0.3 秒涨到 0.8 秒。

只凭时间先后不能认定根因。上面每一条都有修复前后的同一脚本对照数字（第 4 节），以及主进程 CPU 剖析里的调用位置（第 3 节）。

## 2 怎么测的

- **脚本：**`scripts/hx-flow-stress-e2e.ts`，回归脚本，每版必跑。结果写到 `.hxbot-build/hx-flow-stress-e2e/<名字>/report.json`。
- **负载（按需求）：**3 支团队（16、4、4 人）、3 个真人对话（每分钟一句）、6 个定时任务（每 3 分钟），连续 30 分钟；团队做完一轮就开下一轮，整场满载。
- **智能体：**自定义 ACP 假智能体 `scripts/provider-fakes/agents/hx-team-worker.ts`，不调用模型，用 HXBot 自己的工具走完整个协作（开团、看板、交接单分派、交回、收尾），每个回合占 150 MB 内存，流式输出 20～60 秒。
- **每 5 秒逐层记录：**主进程事件循环延迟（每段的 p50、p99、最大，另有一份整场不重置的直方图）、窗口的帧和长任务、主进程发给窗口的消息条数和字节数、智能体进程常驻内存、主进程内存、SQLite 写耗时、同时在跑的回合数、整台电脑的处理器和磁盘压力（/proc/pressure，用来区分“整台电脑停住”和“应用自己卡”）。
- **剖析：**第 22～25 分钟抓 3 分钟主进程 CPU 剖析（`main.cpuprofile`）。
- **停止：**按团队房间的停止键，看 2 秒以后还有没有新的成员回合开始。
- **事件一致（A3）：**`--events=1 --cost-usd=0.01` 再跑 10 分钟：窗口收到的每个回合结束和数据库逐条对照；假智能体记的回合结束总数和数据库对照；每个回合的用量回报和用量记录、金额对照。
- **机器：**云端 Linux 容器，2 核、8 GB 内存，Electron 在 xvfb 下运行。没有账号服务时窗口停在“无法连接账号服务”页，所以窗口的帧数只代表那一页（真实界面另测，见第 6 节）。

## 3 因果链（证据）

| 环节 | 修复前看到的 | 证据 | 修法 |
| --- | --- | --- | --- |
| 调度 | 同时在跑 32 个回合；智能体进程 5.5 GB；分派被拒 252/435 | before 的 `runningMax`、`agentRssMbMax`、`refused` | 桌面端容量闸 B（CONC-01）+ 公平排队（CONC-03）+ 不拒绝只排队（CONC-04） |
| 持久化：频道列表 | 主进程最大的一块 CPU：`list` ← 侧栏 `listChannels` 与 Team API 本机路由，180 秒里 6.6 秒；每次的时间随消息量线性增长 | before、after 的剖析；把库放大 30 倍后每次 209 毫秒 | `hx/flow.py` channel_unread：记住数到哪一条，只数新来的 |
| 持久化：启动时恢复频道 | 启动后主进程卡 26 秒（老库） | aged-before 的剖析：24.3 秒在 `messages` ← `capture` ← `recover` | channel_capture：按 id 读 |
| 持久化：排队检查 | 排队后 `hasAgentAssignmentInState` 180 秒里 4.8 秒，卡顿随时间涨到 0.8 秒 | after4、after5 的剖析 | channel_store：一轮事件循环查一次，分派一变就重查 |
| 调度：频道调度 | `#scheduling` 每次读全部频道的任务，做完的团队房间越积越多 | after6 的剖析 1.4 秒 | channel_scheduling：只读有未完成工作的频道（0.84 秒） |
| 事件传输 | 主进程发给窗口最多 82 条/秒、1.5 MB/秒，没有积压 | before 的 `ipc` | 不是原因，未改 |
| SQLite 写 | 写耗时 p99 0.6 毫秒、最大 13 毫秒 | before 的 `sqlite` | 不是原因，未改 |
| 界面更新 | 窗口最长一帧 250 毫秒，没有超过 2 秒的无响应 | before 的 `window` | 这一页不是原因；真实界面见第 6 节 |

## 5 老库对照（随历史变慢的证据）

把修复后 30 分钟测试留下的数据库里的频道消息复制 30 倍（17,216 条、89 MB，没读过），作为“用了很久的电脑”的数据库。

**频道列表单独计时**（同一库上用修复前、修复后的 `ChannelStore` 各读 4 次；修复后第一次要把历史数一遍，之后只数新来的）：

| | 3 MB 消息 | 89 MB 消息 |
| --- | --- | --- |
| 修复前：每次 `list` | 10 ms | 209～237 ms |
| 修复后：第一次 / 之后每次 | — | 224 ms / 5～12 ms |

**在老库上跑压力脚本 10 分钟**，又查出三处随历史或智能体数变慢的地方：

| 看到的 | 剖析里的位置 | 修法 |
| --- | --- | --- |
| 启动后主进程卡 49 秒 | 49.4 秒在 `ChannelStore.messages` ← `ChannelService.capture` ← `recover`：启动时对每个频道线程做整份快照的 capture，每次读整个频道历史（团队房间有十几个成员线程） | channel_capture：整份快照也按 id 读消息，结果相同 |

## 5a 终态、审计、费用记录不丢（BUG-CONC-01-A3）

`--events=1 --cost-usd=0.01`，10 分钟满载后按停止键，再等 10 秒核对（只算这一轮开始以后的记录）：

| 核对 | 结果 |
| --- | --- |
| 智能体线程的回合结束：窗口收到的 vs 数据库 | 97 / 97，丢 0、多 0、状态不一致 0 |
| 全部回合结束：假智能体记的 vs 数据库（频道线程的回合，窗口按设计只收频道变化） | 184 / 184 |
| 用量：回报了用量的回合 vs 用量记录；回报的金额 vs 记录的金额 | 179 / 178；0.60 / 0.60 美元 |

差的 1 条用量查出两处原来就有的缺陷，都已修好：①上游的频道摘要和路由生成、旁问用了模型但不记用量；②HXBot 自动选模型的“小模型判断”（v1.6.5 起）不记用量。两处都让费用提醒和用量页少算。修法：这三处和记忆整理、网页搜索一样，传 `sideSessionUsageObserver`。修后在老库上再跑 10 分钟核对（aged-after，《并发基线-v1.7.1.json》的 `events`）：智能体线程的回合结束 90 / 90（丢 0、多 0、状态不一致 0），全部回合结束 158 / 158，用量 157 / 157，金额 0.49 / 0.49 美元，一条不差。

## 6 没在这里测到的、要真机看的

- **真实界面：**上面几轮没有账号服务，窗口停在“无法连接账号服务”页。另跑了一轮真实主界面（ui1，2026-11-18）：本机起账号服务（`apps/auth-api` 的 vite dev，端口 3100，注册时的邮箱和短信验证码关掉），注册一个测试账号，压力脚本登录后（`--auth-url=http://127.0.0.1:3100 --auth-account=<文件>`）同样跑 30 分钟。五项门禁全部通过：主进程事件循环整场 p99 18.8 毫秒、最长 0.6 秒；窗口共 108,752 帧，最长一帧 283 毫秒、最长任务 237 毫秒，没有超过 2 秒不响应；同时在跑最多 9 个；分派被拒 0 次；按 3 个团队房间的停止键后，2 秒以后新开始的成员回合 0 个。报告在 `.hxbot-build/hx-flow-stress-e2e/ui1/report.json`，汇总进《并发基线-v1.7.1.json》的 `realUi`。“界面显示已停止”要人看，仍在《上线操作手册》第 1.6 节第一部分第 7 步。
- **冷启动：**云端环境重启后的第一次运行，窗口在开头 5 秒内有一次 2.2～3.4 秒的长任务（之后的热启动 0.3 秒）。只出现在冷启动，不在压力期间。
- **Mac、Windows：**内存读法（vm_stat、内存压力等级、tasklist）和 Windows 的进程树在 GitHub 的真机上测（《客户端构建》第 6.10 节）。2026-11-18 运行 44248506003，5 台全部通过：
  - macOS 15、26（BUG-CONC-01-A4）：总内存 7168 MB；vm_stat 算出可用 3159 MB 和 3277 MB（44%、46%）；内核压力等级 1，HX 读作 normal；`memory_pressure` 说空闲 84%、87%。三者一致。ps 读到 2 个各占 150 MB 的子进程，共 385～387 MB。
  - Windows Server 2025、2022、Windows 11 ARM：tasklist 读到 2 个各 150 MB 的进程，共 366～370 MB；常驻 PowerShell 就绪 0.7 秒、1.1 秒（ARM 31.8 秒），之后每次回答 1～31 毫秒（新起一个 PowerShell 要 2.0～4.4 秒）；进程树 0.3～0.6 秒列出，要停的不含有窗口的应用；停下后有窗口的应用还开着，无窗口的进程已停。
  - 前两次运行 Windows 的“停下后保留应用”没过，是测试本身的问题：测试的根进程是 Node，Node 把自己直接起的子进程放进“根进程关掉就一起关”的作业对象。改成和智能体一样经 `cmd /c start` 打开应用后通过。
  - 8 GB Mac 上开着别的应用时的实际感觉见《上线操作手册》第 1.6 节第一部分。
- **真实模型：**假智能体不调用模型；回合时长、输出量与真实模型不同。

## 7 后续项（不影响这一版）

- `channelsWithOpenWork`（180 秒里 0.93 秒）和 `openTaskIds`（1.2 秒）仍对 JSON 字段做无索引查询，会随任务数增长；彻底解决要加表达式索引，需要一次数据库迁移，留到下一版评估。
- 频道列表的任务计数（运行中、未完成）每次仍逐个任务读 JSON，任务远少于消息，30 倍时约 2 毫秒。
- 按描述生成新智能体的资料（名字、介绍）用了模型但不记用量：那时智能体还没建好，记不到谁名下。
