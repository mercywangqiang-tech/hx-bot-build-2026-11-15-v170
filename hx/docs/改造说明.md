# HXBot 研究版 · 改造说明

本文说明在 OpenBot 源码上做了哪些改动，以及原项目更新后如何同步。

## 1. 改造原则

- **所有改动由脚本完成**：`hx/rebrand.py` 读取 `hx/brand.json`，对 OpenBot 源码逐处精确替换。脚本可以重复运行；原项目代码变化导致某处匹配不到时，脚本会报错并指出位置，不会悄悄漏改。
- **只改对外可见的部分**：产品名、包标识、服务地址、图标、界面文字、统计与更新。在操作系统里登记的链接方式从 v1.5 起改为 `hxbot://`（第 10 节）；从 v1.5.2 起，源码、配置、文档、文件名里所有的 OpenBot 统一改成 HXBot，只留下兼容旧版本必须认得的旧名称（第 11 节）。
- **保留许可与版权**：LICENSE、NOTICE 和所有 Required Notice 原样保留。

## 5. 封堵上游入口（不指向 OpenBot）

`hx/close_upstream.py` 是 rebrand.py 的一步，保证研究版的任何界面、链接、下载、版本检查和数据上报都不会通往 OpenBot（openbot.run、nightly-labs/openbot 的 GitHub、OpenBot 的 Discord / X / 社交账号、应用商店里的 OpenBot 应用）。覆盖桌面端（Mac、Windows）、网页版（含手机浏览器）、安卓端、iOS 端、账号服务和信令服务：

| 类别 | 原来 | 研究版 |
| --- | --- | --- |
| 帮助（?）菜单 | 新功能（上游发布说明）、完整更新日志、指南、加入 Discord、发送反馈（发到 X） | 使用指南：bot.hxallai.com/guide/；服务端：/guide/#server（发布服务器与邀请成员）；下载最新版本：门户下载中心；发送反馈：发邮件到 bot@hxallai.com；助手设置出错时的排查链接：/guide/#faq |
| 服务条款与隐私政策 | 登录页链接上游的条款和隐私政策；手机端“关于”链接上游隐私政策 | 链接研究版自己的《服务条款》（/terms/）和《隐私政策》（/privacy/），中英文各一份；手机端“关于 → 隐私政策”打开 /privacy/ |
| 下载与更新 | 去 openbot.run 下载；查询上游 GitHub 的新版本；“连接手机”二维码指向 App Store / Google Play 上的 OpenBot；手机端“去商店更新” | 全部指向 bot.hxallai.com 的下载页；不再查询上游版本；手机端关闭 Expo 在线更新 |
| 出错页与 404 | 上游官网的页头、页脚（GitHub、X、Discord 链接） | HXBot 自己的页面，只链接网页版和下载页 |
| 上游官网的其他页面 | 账号服务里仍带着（首页、下载、价格、指南、应用市场、更新日志、法律文本等） | nginx 与账号服务（hx-pages.ts）双重拦截，一律转回下载页 |
| 自动联网 | 统计与错误上报（analytics.openbot.run）、读取上游 GitHub 的运行时屏蔽表、上游的 GitHub 应用、MCP 登录时报出的应用身份 | 统计地址改为永不解析的 .invalid 域名（本来就关闭，双保险）；不读屏蔽表；不使用上游 GitHub 应用；MCP 身份为 HXBot（bot.hxallai.com） |
| 文字 | 界面、报错、发给 AI 模型的说明里的 “OpenBot”、上游发布说明、licenses@openbot.run、@OpenBot、openbot.site、Synthetify Labs | HXBot / bot@hxallai.com / 弘犀智能（HX AI）；上游发布说明清空 |
| 分享与联系 | 分享链接、插件链接、联系邮箱、苹果关联域名、iOS 扩展标识、Mac 团队号 | bot.hxallai.com、bot@hxallai.com、com.hxallai.bot 系列 |

**自动扫描**：rebrand.py 最后扫描全部运行代码（约 5500 个文件：桌面端主进程与界面、网页版、共享组件、安卓与 iOS 的界面代码、原生模块（Swift、Kotlin）、iOS 扩展、Expo 配置、上架脚本、随包资源、账号服务对外开放的全部路由、信令服务、15 种语言的界面文字）。只要还有指向上游的地址，或作为文字出现的 “OpenBot”，脚本就报错停止，构建脚本随之中止，不会打出带上游入口的安装包。

**保留的旧名称**：统一改名之后只剩兼容旧版本必须认得的旧名称，清单和理由见第 11 节。

**使用指南、新功能与亮点、服务条款与隐私政策**：原文是 `hx/docs/site/` 里的 Markdown（guide、whats-new、terms、privacy 各有 `.zh.md` 和 `.en.md`），`node hx/scripts/site-pages.mjs` 生成 `hx/server/portal/pages/` 下的 8 个静态页（版式与门户一致），nginx 以 `/guide/`、`/whats-new/`、`/terms/`、`/privacy/` 和 `/en/…` 提供。《新功能与亮点》（v1.6.4 起，用户要求）每个版本加一节放在最前面，旧版本的节原样保留，所以每一版的页面都包含之前各版的内容；每节先写三条左右的“亮点”，再按功能分组写“新增功能”，只写用户看得到、用得到的变化。门户首页的顶栏和页脚、四个页面的顶栏和页脚都有“新功能”链接。中文页按上次的语言选择或浏览器语言自动转到英文页并保留 `#章节`。生成脚本同时检查：英文页不含中文（ICP 备案号与语言按钮除外）、页面和门户首页不含上游名称、中英文章节编号一致、客户端打开的 `#server`、`#faq` 两个章节存在；`--check` 模式确认页面与 Markdown 一致，打交付包时（package-release.sh）自动运行。账号服务（hx-pages.ts）把旧的条款、隐私政策、指南地址转到这些页面。改条款或政策时，中英文两份一起改，并同步核对《隐私政策》里写明的保存期限与服务器设置（备份 30 天、访问日志 200 天）是否一致。

**构建时的唯一上游依赖**：Mac / Windows 安装包里的远程桌面运行时（开源的 Sunshine 与 Moonlight 组件）由打包脚本从 nightly-labs/openbot 的 GitHub Releases 下载预编译包，按 `native-runtime.lock.json` 里的 SHA-256 校验。它只在打包时下载一次；装好的客户端运行时不会访问上游。

## 6. 已知限制

- 从旧版本升级的电脑继续使用原来的数据目录 `~/OpenBot`，新装的电脑用 `~/HXBot`（第 11 节）。
- Slack、Discord、Telegram 机器人、托管网站、iOS 推送依赖额外的密钥和服务，研究版服务器未接入。
- 安装包未做苹果公证和 Windows 代码签名，首次打开需手动允许。
- 应用内更新只有登录后才检查；Mac 版没有苹果签名，更新时由 HXBot 自己替换应用（第 15 节），应用不在“应用程序”文件夹里时只能手动安装。

## 6. Mac 不弹钥匙串密码框；登录动画换成长颈鹿（2026-11-11）

**钥匙串密码框**：原版把登录状态、API 密钥等机密交给 macOS 钥匙串里的“HXBot Safe Storage”加密，网页 Cookie 也用它。研究版没有苹果开发者签名，macOS 每次启动（或每次更新）都把 HXBot 当成另一个程序，弹框要“登录”钥匙串的密码。研究版改为：

| 位置 | 改动 |
| --- | --- |
| `src/main/secret-storage-cipher.ts`（rebrand.py 的 `keychain` 一步） | Mac 上所有机密一律用 HXBot 自己的“保密箱”加密：AES-256-GCM，钥匙是数据文件夹里的 `secret-storage.key`（`~/Library/Application Support/HXBot/`，装过 v1.6 及更早版本的电脑是 `…/HX Bot/`，见第 14 节；权限 0600，只有本账户能读）。Mac 上不再调用 safeStorage。升级、重装安装包都不影响，不用重填 |
| `src/main/hx-defaults.ts`（主进程第一个加载的模块） | Mac 上打开 Chromium 的 `use-mock-keychain` 开关，网页 Cookie 的加密钥匙也不再存取钥匙串 |
| 旧版本留下的值 | 旧值是用钥匙串里的钥匙加密的，读取就会弹框，所以不读，按“已丢失”处理：升级后重新登录一次，之前保存的 API 密钥再填一次；内置浏览器里登录过的网站需要重新登录。填进去之后一直有效 |
| Windows、Linux | 不变：Windows 用系统自带的 DPAPI（不弹框）；Linux 用系统钥匙环，钥匙环失效时用同一个钥匙文件 |

钥匙串里旧的“HXBot Safe Storage”项目不再使用，可以在“钥匙串访问”里删除，也可以不管。

## 9. 按需授权：访问本地电脑和网页前先申请（2026-11-11）

> v1.6.2 起默认改为“最大权限”，判定规则、卡片和设置页见第 16 节；本节记录的是 v1.5～v1.6.1 的做法。

原版的“仅工作区”只限制写入，读取、网络、电脑操控（Computer Use）和内置浏览器都不受限，而且默认是“完全访问”。研究版改为“按需授权”，并作为所有智能体的默认设置（rebrand.py 的 `on_demand_access` 一步，接线在 `hx/access_control.py`，HX 自有代码在 `src/backend/hx-access/`）。

| 要点 | 说明 |
| --- | --- |
| 不用申请 | 在工作区、共享文件夹、客户添加的文件夹和临时文件夹里读取、写入文件；工作区里的普通读取命令（ls、cat、rg、git status 等） |
| 要先申请 | 工作区外的读取、写入、删除；任何删除（包括工作区里）；其他命令；内置浏览器打开或操作网站；截图；网络搜索；把工作区外的文件附到回复里 |
| 怎么申请 | 智能体调用 `request_access`，写明为什么需要、用来做什么、要访问的对象（文件夹、文件、网站、命令、屏幕、搜索）和要做的行为。客户在卡片上勾选允许“读取”“写入”“删除”中的哪几项，也可以在卡片上写附加条件，原话转给智能体；不勾选或跳过即拒绝 |
| 谁能同意 | 只有服务器所有者（桌面端本人或所有者的网页、手机）能授权；团队成员只能拒绝；本机脚本不能代答 |
| 收回 | 本次任务结束自动收回；新任务开始时清掉旧授权；智能体可调用 `release_access` 提前交还；客户按“停止”即结束任务、收回授权 |
| 各服务商 | Codex：每条命令和补丁都先询问（approvalPolicy=untrusted），由授权自动同意或拒绝。Claude：每个工具调用都经过 HX 的钩子判定。Grok 等 ACP 服务商：它们提出的请求带上路径、网址和命令后按授权判定；OpenCode 改为所有工具都先问 |
| 防绕过 | `$HOME`、`~其他用户`、`{a,b}`、`%VAR%` 这类会被展开的写法不算工作区路径；带环境变量前缀、git 全局选项、sed 执行脚本、rg --pre 等要命令授权；`.git` 里不能免授权写入；读不懂的复杂命令只认完全相同的命令授权或“所有命令” |
| 默认与迁移 | 新建智能体默认按需授权；升级后第一次启动时，现有智能体一次性改为按需授权（数据文件夹里的 `hx-on-demand-access.json` 记录已改过） |
| 完全访问 | 保留，要在设置里手动选择，并确认两次（桌面端、网页版、手机端都是） |
| Computer Use | 按需授权时不提供，设置里的开关也不显示 |
| 没有沙盒的电脑 | 原版在 Windows、Linux 上不让 Grok 等服务商使用“仅工作区”；研究版照常启动，由服务商的逐项询问和 HX 的判定把关。Claude 的命令沙盒只在 macOS 上强制 |
| 界面 | 15 种语言把“仅工作区”改为“按需授权”；说明重写，15 种语言都有译文；手机端提问卡片支持多选 |

已知限制（设置里的说明也如实写了）：

- Codex 会把 cat、ls、grep 这类普通读取命令当作安全命令，不经询问直接运行，所以能读到工作区外的文件。要拦住只能改用户自己的 Codex 设置（`~/.codex/rules`），研究版没有这样做。
- Codex 的已知缺口：已批准的命令如果在沙盒里被拒，Codex 会不再询问、直接在沙盒外重跑。所以命令授权按命令前缀给，卡片上写明具体命令。
- Grok 等 ACP 服务商自己读文件时如果不询问，读取拦不住；macOS 上它们的写入仍受沙盒限制。
- 已授权的命令内部做了什么（比如脚本里删文件），HX 看不到。
- 网站上的“删除”和普通按钮分不出来，网站只分读取和写入。
- Codex 自带的网络搜索由 OpenAI 执行，HX 拦不住。
- 真实服务商的端到端测试要在用户自己的 Mac 或 Windows 上登录账号后进行。

## 10. 自有的链接方式与对外名称（2026-11-11，v1.5）

## 12. 和上游一样通过它自己的检查（2026-11-12，v1.5.3）

上游的代码能通过它自己的全部静态检查。到 v1.5.2 为止，研究版只要求“不比上一个研究版差”，这些检查从来没有通过过：改造删掉页面和功能后留下的文字、样式，改造加进去的文字和代码，都被这些检查报出来（v1.5.2：格式与规范 269 个错误，界面文字 864 条问题，其余各项也都不通过）。从 v1.5.3 起标准改为“和上游一样全部通过”，由 `bash hx/scripts/check-gates.sh` 检查，打包脚本会先运行它，任何一项不通过就不打包。

| 检查 | 命令 | 管什么 | 研究版怎么通过 |
| --- | --- | --- | --- |
| 改造结果 | `python3 hx/rebrand.py --check` | 代码就是改造的结果，没有上游的名称和入口，格式已整理 | 见下面“格式” |
| 格式与规范 | `bun run lint` | Biome 的格式、import 顺序和代码规范 | 结果与上游完全相同：0 个错误（警告 188 条、提示 4 条都是上游原有的） |
| 界面文字 | `bun run i18n:check` | 没有没人用的文字；没有译文的文字都登记过 | 删掉没人用的 292 条；研究版的文字都有 13 种语言的译文，不再登记“暂用英文” |
| 界面样式 | `bun run check:ui` | 没有哪个页面都用不到的样式 | 删掉 3 个样式文件里的 6 条规则，和 1 个没人引用的样式文件 |
| 图片目录 | `bun run check:assets` | 图片只放在登记过的目录 | 登记 `hx/assets/`、`hx/docs/assets/` |
| 文档链接 | `bun run check:doc-links` | 文档内部链接有效 | 改名时把指向标题的链接一起改（`brand_rename.py` 的 HEADING_LINK） |
| 模型内容大小 | `bun run check:agent-context` | 每次对话发给 AI 模型的说明和工具清单不变大 | 按研究版的实际大小重新登记（见下） |
| 严格类型 | `bun run types:ratchet` | 严格类型选项下没有新增错误 | 服务器设置正式登记进类型定义，不再用类型断言 |
| 没人用的代码 | `bun run knip:check` | 没有用不到的文件、依赖、导出 | 弘犀自己的删掉；上游文件里的登记（见下） |
| 门户页面 | `node hx/scripts/site-pages.mjs --check` | 使用指南、新功能与亮点、条款、隐私政策页面与 Markdown 一致 | 一直有的检查 |

实现在 `hx/upstream_checks.py`（改造的一步，在改名之前运行）和 `hx/brand_rename.py` 的 `finish`（全部步骤之后）。

**格式。**上游的每个文件都是用 Biome 整理好的。改造把名字换短、把域名换长、加了新的 import 以后，有的行该合并或折开，import 的顺序也变了（v1.5.2 有 120 个文件因此不合格，其中 101 个是外语文字文件）。现在改造的最后一步用仓库自带的 Biome 把整棵树整理一遍，只整理格式和 import 顺序。上游没动过的文件本来就是整理好的，不会变。改造里插入 import 的地方都按字母顺序放好，Biome 不会再挪动它们，重复运行改造时才认得出已经改过。已经改造好的源码这一步什么都不改，不需要 Node 工具。

**弘犀的静态网页不归 Biome 管。**门户首页（`hx/server/portal/index.html`）是手写的，脚本故意用旧写法以兼容旧浏览器；使用指南、条款、隐私政策页面和部署文档的网页是脚本生成的。Biome 的规则是给应用代码定的，用在这些页面上报的 371 条都不是问题（例如标题旁对读屏软件隐藏的 “#” 链接被报成“链接没有内容”）。它们在 `biome.json` 里划出去，由 `site-pages.mjs --check` 检查。弘犀自己的脚本和代码（`hx/scripts/*.mjs`、`hx-*.ts`）照常受检，报出的问题都已改掉。

**没人用的界面文字。**清单在 `hx/unused-messages.txt`（上游原来的键名），15 种语言里一起删。其中约 250 条是上游官网宣传页的文案（功能介绍、定价、联系表单），其余是邮件验证码登录界面和帮助菜单上游入口的文字。检查以后报出新的 “is not used” 时，确认是改造造成的，把键加进清单；清单里的键如果又有代码用到，类型检查会报错，把它从清单里去掉。

**研究版文字的译文。**研究版加的界面文字（登录注册、按需授权、保密箱提醒、帮助菜单、手机端连接页等）和被研究版改了意思的上游文字，英文和中文写在各自的改造步骤里，阿拉伯语、德语、西班牙语、法语、希伯来语、意大利语、日语、韩语、荷兰语、波兰语、葡萄牙语、俄语、土耳其语的译文都在 `hx/translations.py`（v1.6 起，共 74 条）。`upstream_checks.py` 的 `translated` 一步把它们写进各语言的文件：有这条就改成译文，没有就按英文的顺序加进去。`rebrand.untranslated()` 不会把有译文的语言登记成“暂用英文”。

以后加新文字或改了某条文字的英文：先在改造步骤里写好英文和中文，再在 `translations.py` 的 KEYS 里登记这个键、在 13 种语言的 PHRASES 里写译文（几个键英文相同时可以共用一句）。暂时译不了的，不登记也行：`i18n:check` 会报 “is not translated”，这时在改造步骤里用 `r.untranslated(add=…)` 登记，界面上显示英文。译文的约定写在 `translations.py` 开头：产品名照原样；界面上的名称用这种语言界面里的写法；门户页和授权卡片只有中英文，所以译文不引用上面的按钮名；占位符原样保留（`check_placeholders()` 检查）。

**模型内容大小。**研究版加了按需授权（申请访问的工具和规则说明）和保密箱的规则，这些是有意加的：智能体说明多约 400 字节，工具清单多约 2 KB，工具参数和描述各多约 1 KB。上限按研究版的实际大小登记在 `tools/agent-context/budget.json`（数值在 `upstream_checks.py` 的 AGENT_CONTEXT_BYTES，旁边注着上游的数值）。以后研究版再加内容，这项检查同样会拦住；确实要加时改这组数值。

**没人用的代码。**弘犀自己的文件里没人用的导出，去掉 `export`，完全没人调用的函数删掉。上游的 34 个文件里有一些导出因为宣传页、邮件验证码登录、毛绒头像被去掉而没人用了：这些文件保持上游原样，按上游对“固定不动的文件”的做法登记在 `knip.config.ts` 的 `ignoreIssues`（清单在 `upstream_checks.py` 的 LEFT_AS_UPSTREAM）。理由：打包时没人用的代码本来就不进安装包，删掉它们没有好处，却会让以后同步上游时多出一批容易对不上的改动。上游官网首页用的 `@paper-design/shaders` 依赖同样保留并登记，这样 `bun.lock` 与上游一致。

**提交前检查。**`bun install` 会启用提交前检查。上游的那一个会用 Biome 自动改写暂存的文件再重新暂存，并按上游的发版流程检查更新说明：提交出去的代码可能不再等于改造的结果。研究版换成自己的 `hx/githooks/pre-commit`，只检查、不改任何文件：① 新加入的 `.env`、签名密钥、证书等机密文件不能提交；② `python3 hx/rebrand.py --check` 通过；③ 暂存文件的格式和规范没有问题（只报告）。上游的 `.githooks/` 留着不用。

**同步上游之后**这些检查报错的处理：格式问题运行 `python3 hx/rebrand.py`；`i18n:check` 报 “is not used” 或 “is not translated”、`check:ui` 报用不到的样式、`knip:check` 报没人用的导出，说明上游的改动和研究版删掉的东西有了新的交集，按上面各段在 `upstream_checks.py` 或 `unused-messages.txt` 里补上。

## 13. 注册账号：每个人自己的密码（2026-11-12，v1.6）

以前大家共用一个登录口令（HX_LOGIN_PASSWORD）。v1.6 起每个人在门户注册自己的账号：邮箱 + 密码登录，注册时填写用户名、手机号码、职位、公司名称，并验证邮箱（默认开启）和手机号码（阿里云短信，默认开启），两项验证都可以在 .env 里关闭。微信、支付宝、抖音、Apple、Google、Facebook 六家登录做成开关：哪家的密钥填进 .env，哪家的按钮就出现在门户上。注册完全开放；需要时用 HX_ALLOWED_EMAILS、HX_ALLOWED_EMAIL_DOMAINS 只对名单开放。

**设计。**

- 登录接口不变（先邮箱、再“验证码”一栏），所以网页版、桌面端、手机端的登录只换了文字：第二步核对的是这个邮箱自己的密码。接入点在 `auth-service.ts` 取哈希的两处（rebrand.py 的 login_password 步骤），由 `HxAccountSignIn.startHash / verifyHash` 提供。
- 注册、找回密码、第三方登录走完后，模块发一张一次性登录票据（一条登录挑战 + `hx_tickets` 标记，5 分钟内有效），门户拿它调原有的 `/api/browser/email/verify` 换登录状态。登录会话和 `users` 表仍由上游代码管理。
- 数据按邮箱挂在 `hx_accounts`（迁移 `9001_hx_accounts.sql`，编号放在上游所有迁移之后），不依赖 `users.id`。第三方身份在 `hx_identities`，没走完的注册、找回密码、第三方登录在 `hx_pending`（验证码只存哈希）。数据库就是账号服务自带的 SQLite（D1），不另装数据库。
- 密码：PBKDF2-HMAC-SHA256，100000 次（workerd 的上限），每个账号独立的盐；8～32 个字符，同时含字母和数字。
- 频率限制用上游的 `auth_rate_limits` 表（键只存哈希）。上游的定时任务每 5 分钟删掉开始超过 15 分钟的计数，所以按天计的计数（同一手机号每天最多 10 条短信）存在窗口的结束时刻上，否则每 5 分钟就被清零。
- 第三方登录：`/api/browser/hx/oauth/<平台>/start` → 平台授权页 → `…/callback`。回来的浏览器必须带着出发时的 Cookie（`hx_oauth`）；Apple 用表单 POST 回来，先 303 转成 GET。没绑定过的第三方账号要先注册（或绑定已有账号），之后直接登录。接口都在 `/api/browser/hx/` 下（nginx 已放行 `/api/`）。
- 老账号（用共用口令登录过、`users` 里有、`hx_accounts` 里没有）：在门户用原来的邮箱走注册，设置自己的密码，原来的服务器和成员关系都保留。能发邮箱验证码时凭验证码；邮箱验证关闭时凭原来的共用口令（HX_LOGIN_PASSWORD 仍在 .env 里时）。共用口令本身不再能登录。

**文件。**服务器端在 `apps/auth-api/src/server/hx-accounts/`（config、store、secrets、service、providers、mail、http、index）；接线在 `hx/accounts.py`（`routes/api/browser/$.ts`、`request-auth.ts`）和 rebrand.py 的 login_password 步骤。服务器设置：`hx/server/.env.example`、`account/entrypoint.sh`（把设置写进运行变量）、`scripts/set_env.py`（校验、`--show`、`--test-mail`、`--test-sms`、`--file`）、`scripts/users.sh`（查看用户、重置密码、停用和启用）、`scripts/delete-account.sh`（同时删注册资料）、`scripts/check.sh`（发信邮箱、短信、每家第三方登录）。`hx/scripts/check-server-vars.py` 在编译服务器时核对每一项设置都能从 .env 到达账号服务。门户页的注册、找回密码、绑定表单在 `hx/server/portal/index.html`。

**已知限制。**

- 六家平台和阿里云短信都按公开的接口说明实现，用本地替身验证了请求、签名和整条流程，没有用真实密钥连过真实平台。
- 短信验证只支持中国大陆手机号（国内短信模板）；关闭手机验证后可以填国际号码。
- 桌面端、手机端应用里没有第三方登录按钮：用第三方账号注册的人注册时也设置了密码，在应用里用邮箱 + 密码登录。
- Google、Facebook 的接口在中国大陆的服务器上连不上，只适合部署在境外的服务器。

**怎么选模型。**每个模型按名称和提供方判断档位（S 最强，A、B、C 依次）、能不能看图、窗口多大、免费 / 订阅 / 按量付费；某类工作在中等难度下需要的档位：闲聊 C，写作、小改代码、数据、看图、长资料、电脑操作 B，多文件编程、方案与推理 A；难度高加一档、低减一档；“免费优先”在难度不高时再减一档。打分时免费最优先，档位不够扣分最多；当前模型和同一提供方各有一点加分，差两分以内不换。建议卡里“定方案”和“检查”两个角色按“质量优先”、难度高来选。

**对话里的那一行。**每件新工作开始前写一行，例如“自动选模型 · 写作：由 GLM-5.3-Flash Free 来做。”或“自动选模型 · 看图：换用 Nemotron 3.5 Super VL Free。”；接着上一条说的短消息不再写。文字按英文存、各端按自己的语言显示，所以网页版和手机端不升级也能看到（手机端旧版本可能显示英文）。

**和方案不一样的地方。**① 模型下拉里没有加“自动”一项：上游的模型选择器很大，改它要动共用界面的三层；改为在“模型”“备用模型”下面加一节，开关在这里。② “做不下来时换更强的模型”不是两个按钮，而是一行小字请用户回复“重做”（网页版、手机、外部聊天里都能用）；“改用……重答”同样是在消息里点名模型。③ 频道里的工作这一期不换模型（频道按成员当时的模型登记）。④ 网页版和手机端没有设置这一节。⑤ 判断模型在这里没有用真实的模型测过。

**测试。**`src/backend/hx-auto-model/*.test.ts` 和 `HxAutoModelSection.test.tsx`。判断的准确率如实写：第一组 270 条是写规则时用来调的，现在 98.5%；第二组 90 条第一次测 56.7%，用它加宽词表后是 100%；第三组 90 条在加宽词表之后才写、只测了一次：66.7%（60 条对），其中 30 条把握低于 0.7、会交给判断模型；按第三组做了几处一般性的修正（GitHub 不是 git、“开一家新店”不是打开应用）以后是 84.4%。看图和长资料两类三组都是 100%。所以规则单独用时并不准，“规则 + 小模型”是默认；规则和小模型都没把握时不换模型。

## 22. “添加服务商”里连接 OpenCode 的全部服务商（2026-11-14，v1.6.5）

**目的。**HXBot 以前只用 OpenCode 的免费模型和 OpenCode Go 密钥；OpenCode 能接的其他服务商（OpenAI、DeepSeek、Kimi、智谱、通义、GitHub Copilot 等），要用户自己在终端里运行 `opencode auth login`。这一版把 OpenCode 的整份服务商清单放进 HXBot：在“添加服务商或助手”（模型面板“+”→ 服务商设置 → 添加）里多一组“OpenCode 全部服务商”，服务商设置页底部也有一行入口。连上的服务商，模型出现在智能体的模型选择里（归在 OpenCode 下，按服务商名分组），也进入“自动选择模型”的候选范围。

**清单从哪里来。**OpenCode 2 自带一个本机服务（`opencode serve`），里面有连接接口：`GET /api/integration`（全部服务商和每家的连接方式、已有连接）、`POST …/connect/key`（API 密钥）、`POST …/connect/oauth`（网页登录，返回登录页地址；`GET …/connect/oauth/{id}` 查状态，`…/complete` 交登录页给的代码）、`POST …/connect/external`（本机已有的凭据，例如 AWS 配置、gcloud、Claude Code 登录）、`DELETE /api/credential/{id}`（断开）。HXBot 临时起一个这样的服务：只听 127.0.0.1、端口随机、每次一个新的随机密码（只放在这个进程的环境变量里），在一个空文件夹里启动（不加载任何项目的 OpenCode 配置、插件和命令）；5 分钟没有请求、也没有正在等的网页登录就关掉，HXBot 退出时一起关掉。凭据由 OpenCode 自己保存在它的数据文件夹里，和 `opencode auth login` 一样，HXBot 不另存；`opencode acp`（智能体用的那个进程）读的是同一个文件夹，所以连完后 HXBot 等 OpenCode 空闲时重启它，新模型就出现。OpenCode 2.2.5 的清单有 238 项，其中 5 项是网页搜索服务（Exa、Firecrawl、Parallel、Tavily、TinyFish），不是模型服务商，不列出，剩 233 家。

## 23. 协作（二）：多智能体无缝协作（2026-11-14，v1.6.6）

**目的。**上游已经有频道（几个智能体共用的聊天，带头的分派子任务、转交整件事、成员交回结果）和 `send_to_channel`，但都要用户自己建频道、拉成员、写说明，结果也不会回到原来的对话。这一版把它们接到建议卡上：用户在建议卡上点“开始”，HXBot 自动组队、建协作房间（就是一个频道）、发简报；成员之间用固定格式的交接单交接，共用一块任务看板；进度和结果回到用户原来的对话。设计见 Project 文档《HXBot-智能体协作与应用工作流-方案》第 7 节。

**发起人不进团队。**用户正在对话的那个智能体（发起人）留在用户身边：它组队、转达用户的话、叫停、换人、把结果讲给用户听，自己不做房间里的工作。这样结果可以作为“带头的发来的消息”送到发起人的对话里（上游的消息不能发给自己），用户在原来的对话里也一直能说话。

## 24. 电脑操控（二）：打开应用后一步步操作；协作的进度卡和更大的团队；新功能默认最强（2026-11-14，v1.6.7）

**目的。**用户 2026-11-14 要求：“打开电脑的应用后，一步步操作应用，控制鼠标和键盘……按照客户要求自己规划进行一步一步操作”；同一天又定，v1.6.6 留下的五处出入（技能和连接器没有合并、进度没有进度条、上限只能在桌面端改、没有用真实模型测、《隐私政策》没改）都在这一版解决，从这一版起新功能默认用最强的方式、设置要少、升级后醒目地说明，团队最多 20 人。用户又把 v1.6.8 里“驱动缺授权时说清缺哪一项、一键打开系统页”的一小块提前到这一版（回复“提前”）。

**一步步操作的做法。**上游随包带着电脑操控驱动 cua-driver 0.34.0（后台点击、输入、读窗口的控件树），模型直接用它的 MCP 工具时要自己选窗口、看坐标、判断有没有做成。研究版在它上面加了三个工具，模型说“做什么”，本机负责“怎么做、做没做成”：

- `computer_plan`：把计划的步骤（1～12 行）写成对话里的进度卡；之后每一步做完、失败或停下，卡片原地更新。
- `computer_look`：读一个窗口，给模型一份短提纲（每个能操作或能读的控件一行：编号、种类、名字、值），不截图。
- `computer_do`：一次做最多 12 步：点击、双击、右键、输入、按键、组合键、滚动、拖动、菜单、等待。控件按“种类 + 名字”找（只给种类时，这一种只有一个就用它），不按位置；点击先在后台点，不行再到前台点，最后按位置点；在输入框里输入前先在前台点一下输入框，之后文字和按键都发给前台的应用，输入后再读一遍输入框，文字没进去就算失败；每一步可以写“做完应该看到什么”，由驱动或 HXBot 自己读窗口核对；第一步不成就停下，说明原因并附上最接近的几个控件。名字里有发送、付款、购买、删除、发布（中英文）的一步先停下（状态 confirm），要用户在对话里同意后再带 `confirmed` 重做。
- 停止键：⌃⌥Esc（Windows：Ctrl+Alt+Esc），在主进程注册为全局快捷键，按下后所有智能体在这台电脑上的步骤在下一步之前停下，15 秒内驱动的调用一律拒绝，进行中的进度卡显示“已停止”。
- 三个工具只在工具目录里（不随每次对话发送），给模型的说明多一句怎么用；屏幕上读到的文字只当资料。

**驱动缺授权时（v1.6.8 提前的一块）。**在 Mac 上驱动要“屏幕录制”和“辅助功能”两项授权，缺一项就不启动，以前模型只得到一句“没有运行”。现在 `computer_look`、`computer_do` 发现驱动没在听时，先经主进程问一次驱动（授过权的就此启动、接上）；还缺授权时打开系统设置里缺的那一页和 HXBot 的授权步骤窗口（和“设置 → Computer Use”里的“授权”按钮一样），在对话里写一行说清缺哪一项，并告诉模型请用户去打开、打开后再试；同一页、同一行两分钟内只出现一次。

**协作的改动。**① 技能：组队时汇总各成员工作区（`.agents/skills`、`.claude/skills`）里的技能，最多 60 个，写进简报和看板（“团队技能表”：技能名、用途、在谁的工作区、文件路径），任何成员都能读那个文件照做；新建的成员带上发起助手的技能；简报写明连接器整台电脑共用。② 进度卡：团队的进度改为发起人对话里的一张进度卡（标题是交接次数和用时，每一步一行“步骤 · 成员”，等待中的步骤标出），原地更新；以前一行行的“交给”“交回”小字不再写（转交、失败、停住等少数几行保留）。③ 上限按用户的话：`start_team` 多了 `limits`（人数、分钟、交接次数，只放用户说了的），`team` 多了 `limits` 动作（运行中的团队改时间和交接次数，时间从团队开始算），网页版和手机上说也一样，手机端不用改。④ 规模：团队最多 20 人、建议卡最多 20 个角色和 30 步（角色多于卡片能放的时候写在卡片正文里）；同时干活的成员数按内存定（每 2 GB 一个，2～10 个），超过时分派会被退回并说明“等一个做完再分派”。

**默认最强、设置要少。**自动选择模型默认打开、倾向“质量优先”（只改没有保存过设置的智能体）；团队默认最多 20 人、240 分钟、80 次交接；助手设置里团队上限收成一行摘要，打开“调整上限”才显示细项。升级后第一次打开时，上游的“新功能”窗口显示 `hx/release-notes.json` 里这一版的几条（每条先说好处，再说在哪里设置），“查看全部更新”打开门户的《新功能与亮点》；`hx/close_upstream.py` 生成这个窗口读的 `whats-new-releases.json` 和中文版。

## 25. Mac 的隐私与权限：固定签名、一键授权、装应用；保密箱自动登录（2026-11-14，v1.6.8）

**目的。**助手“电脑整理”交来的《HXBot 桌面操作能力失败复盘与修正需求》（F1～F6）里，Mac 上的问题根子是四个：每一版的签名都不一样，macOS 把升级后的 HXBot 当成新应用，授权全部作废，系统设置里却还显示打开；授权要两项都给，驱动才启动；授权全靠用户自己在系统设置里找；模型自己的命令在沙盒里装软件、截屏、往“应用程序”里放应用都被拦。用户 2026-11-14 11:27 同意《HXBot-Mac隐私与权限-最优方案》（两件事都按推荐：先用自签的固定证书，开发者账号批下来再换 Developer ID；应用命令和换路移到 v1.6.9），并要求“HXBot自己点打开，最后让用户自己输入密码或者指纹！”；12:28 又要求“Vault 密码自动登录有硬性拦截，改成不拦截！只要支付时候拦截，其他都不拦截！在V1.6.8完成”。

**做法。**

- **固定签名。**`dist:mac` 的最后一步改由 `hx/scripts/mac-dist.ts` 运行 electron-builder：有 `HXBOT_MAC_IDENTITY` 就用它签名（加固运行时、`build/hx-entitlements.mac*.plist`；自签证书不要苹果的时间戳），没有就照旧不签名并说明。证书由用户在自己的 Mac 上运行一次 `hx/scripts/mac-signing-cert.sh` 生成（RSA 3072，10 年，用 Mac 自带的 LibreSSL，钥匙串和 GitHub 的 Mac 机器都读得了），用 `gh` 直接写进打包仓库的 Secrets，指纹写进仓库变量 `HXBOT_MAC_CERT_SHA1`，备份留在用户的 Mac 上；证书和密码不经过对话。GitHub 打包时 `mac-signing-keychain.sh` 把证书装进临时钥匙串并信任（几步都限了时，不会因为等一个没人点的密码框卡住），`mac-signing-check.sh` 核对签名身份（应用标识 + 登记的指纹，或以后的团队号）、加固运行时、权限声明和 Info.plist 的用途说明，不对就不出 Mac 安装包；`upload-downloads.sh` 在 Mac 上上传前再核对一次 zip 里的 HXBot.app，没有固定签名的不上传（测试包用 `HXBOT_ALLOW_UNSIGNED_MAC=1`）。
- **只要辅助功能。**驱动在 Mac 上只要“辅助功能”就算准备好（`accessibility_ready`）；一步步操作读的是控件提纲，不截图，“屏幕录制”只给截屏和看图兜底用，两项仍都列在“设置 → Computer Use”里。
- **一键授权。**“授予”按钮（设置里和对话里的授权卡同一套）：先看这一项对这一版是否真的有效，无效时用 `tccutil reset <服务> <应用标识>` 清掉 HXBot 自己的旧条目（不要管理员密码，不碰别的应用），再打开那一页；“辅助功能”按 macOS 的规定由用户点一下开关，HXBot 每秒看一次，打开后接着打开“屏幕录制”那一页并经电脑操控驱动按下 HXBot 那一行的开关（`grant-press.ts`：按“<应用名>_Toggle”找开关，先后台点，不行再前台点），macOS 随即要密码，用户输入密码或按指纹。“App 管理”同样由 HXBot 自己按。授权步骤窗口多一行说明谁来开这个开关（`grant_text`，15 种语言；窗口高度 424，按 15 种语言里最高的俄语 422 定）。
- **移到“应用程序”。**HXBot 不在“应用程序”文件夹里运行时（下载文件夹、磁盘映像），每个版本第一次打开问一次，同意就用 Electron 的 `app.moveToApplicationsFolder` 移过去并重新打开（`src/main/hx-move-to-applications.ts`）。
- **装应用。**新工具 `computer_install`（`src/backend/hx-computer/install.ts`）：.app、.zip（`ditto -x -k`）、.dmg（只读挂载，装完卸下）里的应用复制到“应用程序”；.pkg 交给系统的安装器，密码由用户输入。装之前读出版本、签名（`codesign -dv`）和是否公证（`spctl`），写进回答；已经装了时先回 `confirm`，模型在对话里问过用户、得到同意后带 `replace: true` 再调；正在运行的先请用户退出。替换的顺序是：新版复制到隐藏的临时名字，旧版改名为“名字 旧版本号.app”，新版改成正式名字，旧版放进废纸篓（在访达里看得到，可以放回）；中途失败就把旧版放回去。macOS 不让替换时（EPERM），打开“App 管理”那一页并自己按开关，回答 `needs-permission`。不去掉系统的隔离标记。
- **沙盒。**最大权限下 OpenCode 每个工具都先问 HXBot（`hxOpenCodeOnDemand`），所以在 Mac 上也不进进程沙盒；其他用沙盒的服务商保留沙盒，放开 Homebrew、npm、pip、cargo、bun 的安装和缓存文件夹，给模型的说明里写明装应用用 `computer_install`、截屏用 `capture_screen`（`src/backend/hx-access/sandbox.ts`）。
- **工具检索（F5）。**空查询列出全部工具；中英文的常用说法（截图、点击、关闭应用、安装……）也能找到对应的工具；找不到时给出最接近的工具，并说清是没有这个功能还是这个智能体没有这个工具（`src/backend/agent/hx-tool-search.ts`）。
- **全屏时关闭不黑屏。**用户 2026-11-14 15:22 报：Mac 上“最大化后黑屏，有时候死机”，补充说是点关闭按钮后整个桌面变黑，切到别的应用就好。原因：Mac 上点关闭时主窗口不关、只隐藏（Dock 图标再叫回来），窗口在全屏时被隐藏，它的全屏空间留下来，空的、整块屏幕是黑的。改为先退出全屏，macOS 报告已退出后再隐藏，2 秒内没有报告也照样隐藏（步骤 `window_fixes`，`src/main/hx-full-screen.ts`）。
- **保密箱。**最大权限下，用保存的密码登录（含验证码）和删除保密箱条目不再要确认；在网页上填银行卡（付款）照旧每次确认、只能“允许一次”；改动工作区以外的文件、管理员命令、密钥文件夹照旧先问。上游“助手在这个网页上运行过脚本就不自动填密码”的保护按用户的选择去掉（`hx/vault_login.py`）。

## 26. 电脑操控（四）：应用命令、脚本，四条路线自动换路（2026-11-14，v1.6.9）

**目的。**统一排期第 6b 行（从 v1.6.8 拆出，用户 2026-11-14 同意；方案见「HXBot-v1.6.8-电脑操控真机打通-方案」④⑤）：能用命令一步做到的事，不让助手截图、一步步点；控制别的应用和运行脚本都在 HXBot 主程序里做，不经过助手的命令行（Mac 上助手的命令在沙盒里，`osascript` 控制不了别的应用）。

**做法。**

- **应用命令 `computer_app`**（`src/backend/hx-computer/app-control.ts`）。动作：`list`（运行中的应用）、`front`、`hide`、`quit`、`window`（左半边、右半边、最大化、居中）、`default`（默认浏览器、邮件、按文件类型）、`menus`、`menu`（Mac 应用的菜单）。Mac：先用 JXA 的 `NSRunningApplication`、`NSWorkspace`、Launch Services（直达），不行再用“系统事件”的 AppleScript（命令）；值都经环境变量或参数传进脚本，不拼进脚本文字。Windows：PowerShell（`-EncodedCommand`，user32 的 `SetForegroundWindow`、`ShowWindow`、`MoveWindow`、`WM_CLOSE`）；菜单交给逐步操作。返回的 JSON 用 zod 核对。
- **退出。**先正常退出，6 秒内核对进程已经结束；没结束（多半在问要不要保存）回 `waiting`，保存框交给用户；`force` 没有 `confirmed` 时回 `confirm`，模型在对话里问过用户、得到同意后才强制退出。
- **默认应用。**Mac 上用 Launch Services 改，最多等 6 秒读回核对；读回不是要的应用（改浏览器时 macOS 弹框确认，macOS 26 上改文件类型也可能弹）回 `confirm-dialog`，让用户或逐步操作去点。Windows 只读 `UserChoice`；要改时打开“设置 → 应用 → 默认应用”，回 `page`，由逐步操作去点（Windows 不让程序直接改）。
- **菜单命令。**读出菜单栏的菜单和命令；点的命令名像“删除”“发送”“清空”时先回 `confirm`。
- **运行脚本 `computer_run`**（`src/backend/hx-computer/run-script.ts`）。AppleScript、JXA（写进临时文件交给 `osascript`，多行脚本原样到达）、快捷指令（`shortcuts run`，输入输出经临时文件）、PowerShell（`-EncodedCommand`）。要管理员权限的（`with administrator privileges`、`sudo`、`-Verb RunAs`）一律不运行；删除、发送、付款、关机这类先回 `confirm`。输出最多 8000 字，只当资料。macOS 回 -1743（不让控制那个应用）时打开“隐私与安全性 → 自动化”，回 `needs-permission`；控制别的应用的脚本超时，多半是 macOS 在问“是否允许 HXBot 控制……”，也回 `needs-permission`，请用户点“好”后再来。
- **四条路线自动换路。**每个结果写明 `route`（`direct`、`command`）和 `tried`（试过哪条、为什么不行）；命令也做不到时回 `use-steps`，说明用 `computer_look`、`computer_do`（控件），最后才用 `capture_screen`（看图）。
- **命令的结果不再卡住。**`hxRun`（`src/backend/hx-computer/runner.ts`）：命令启动的程序（例如经 `cmd /c start` 打开的记事本）会一直占着输出，Node 的 `execFile` 要等它结束才给结果；现在命令自己结束 2 秒后就给结果。GitHub 的 Windows 上真机检查因此卡了 19 分钟才查出来。
- **工具检索和说明。**“退出”“默认浏览器”“菜单”“AppleScript”“快捷指令”“PowerShell”“Excel”等中英文说法找到这两个工具（`src/backend/agent/hx-tool-search.ts`）；沙盒的说明里写明控制别的应用用 `computer_app`、运行脚本用 `computer_run`（`src/backend/hx-access/sandbox.ts`）；`src/main/hx-computer-driver.ts` 加了打开“自动化”那一页。
- **真机检查。**`src/backend/hx-check/app-run.ts`（A1～A10），在 macOS 15.8.2、26.7.2 和 Windows Server 2025 上跑：列出应用、切到前台、摆窗口、读菜单并点“编辑 › 全选”、“删除”菜单先问、隐藏、正常退出并核对、运行 JXA 或 PowerShell、有没保存的改动时退出、读默认浏览器、改默认应用。检查程序每一项做完就写到运行日志里，每一段有时限（`scripts/hx-real-check.ts`）。GitHub 的 Mac 上没有人点“是否允许 HXBot 控制文本编辑”的框，A8 记“提醒”。

**研究版自己的文件。**

| 位置 | 内容 |
| --- | --- |
| `src/backend/hx-computer/app-control.ts` | 应用命令（Mac、Windows） |
| `src/backend/hx-computer/run-script.ts` | 运行脚本 |

**接进上游的地方。**没有新的步骤：两个工具登记在 `src/backend/hx-computer/tools.ts`（`computer_app`、`computer_run` 的说明和参数）和 `computer.ts`，和其他电脑操控工具一样只在开了 Computer Use 的助手的工具目录里，经工具检索找到。

## 27. 不打扰其他应用（2026-11-15，v1.7.0）

**目的。**用户 2026-11-14：“HXBot经常影响其他应用的运行！在V1.7.0必须完全解决！Windows也会存在这样的问题！”，选了五种情况：别的应用变卡、风扇响；焦点被抢、窗口乱跳；快捷键、复制粘贴失灵；别的应用卡死或退出；经常断网。之后要求“全面、无死角、穷举式核查代码、测试三遍”，再扩到全系统的所有功能。

**做法。**上游文件的改动都在一步 `hx/quiet.py`（步骤 quiet），HX 自己的代码：

- **高亮框**（`src/main/hx-quiet.ts`）：`HxRimQuiet` 决定每一跳读不读驱动（`hide`、`keep`、`read`），轮询 250 毫秒，驱动 15 秒内有动作才读，两次读之间至少 500 毫秒。高亮框不转发鼠标；灵动岛、停靠栏用 `hxIgnoreMouse`，Windows 上每 100 毫秒看一次鼠标，靠近窗口 32 像素内才转发（转发要装全局低级鼠标钩子）。
- **按键**（`src/backend/hx-computer/front.ts`、`steps.ts`）：`HxFrontWatch.front()` 读最前面的应用（Mac：NSWorkspace；Windows：GetForegroundWindow 的进程和窗口句柄）。前台输入的步骤发键之前，最前面的不是目标应用（进程或窗口都不对）就停下，不发键、不拉回；一次看到目标在前面，2 秒内的后续按键不再看。发过按键的一次操作结束时 `releaseModifiers()`。
- **先发通知**（`src/main/hx-ask-first.ts`）：`HxAskFirst` 在用户用 HXBot 时直接打开（同一页 60 秒内一次），在别的应用时发通知（10 分钟内一次）、点了才打开；用在授权页、App 管理页、自动化页（`hx-computer-driver.ts`）。远程控制询问（`remote-control-question.ts`）在别的应用时先等通知被点（30 秒），Dock 弹跳、Windows 任务栏闪烁。Mac 自动更新的安装脚本多了第 5 个参数，0 时 `open -g`。
- **剪贴板**（`hx-computer-driver.ts` 的 `hxClipboardKeep`）：type_text 前记下类型和文字，变了就等 300 毫秒放回；只读文字，原来不是纯文字的不放回（读每种格式会让复制它的应用当场生成，大复制要几秒）。GitHub 上核对过驱动打字不碰剪贴板（S9）。
- **停止键**（`hx-computer-stop.ts`）：每秒看一次有没有电脑工具在运行、驱动最近一分钟有没有动作，有才注册 Ctrl+Alt+Esc，没有就注销。
- **优先级**（`runner.ts` 的 `hxRunBackground`、`hx-process-keep.ts` 的 `hxLowerAgentPriority`）：目录读取 `PRIORITY_LOW`；`provider-processes.ts` 登记服务商进程时设 `PRIORITY_BELOW_NORMAL`，它启动的命令继承。
- **读窗口上限**（`src/main/hx-driver-bounds.ts`）：驱动代理（`cua-driver-action-tap.ts`）按整行转发请求，没写 `max_elements`、`timeout_ms` 的 `get_window_state` 补上 1500、3000；别的行逐字节不变。
- **网页标签**：`browser-host.ts` 的空闲清扫给两分钟没用的标签打开后台节流，助手再用时关掉。
- **网络**（`src/main/hx-network.ts`）：`HxPacer` 一个预算、`HxPacedStream` 按速度放行；Mac 的下载自己按 2 MB/s 走，electron-updater 由 `hxPaceUpdater` 换掉执行器的 `createRequest`，回调拿到的是按速度放行的流（会话的 `enableNetworkEmulation` 管不到 net 模块，在 Electron 44 里实测）。远程桌面 `max_bitrate = 10000`。
- **进程树**（`hx-process-keep.ts`）：Windows 上 `stopWindowsProcessTree` 先用 PowerShell 列出整棵树（4 秒），有可见窗口的进程和它下面的留下，其余按 PID `taskkill /F`；列不出来照旧 `/T`。
- **自动选择模型**（`hx-auto-model/router.ts`、`classify.ts`）：工作所在的对话或任务已经有服务商会话（`continuing`），当前模型能接（图片、长资料）时保持模型和推理强度；打招呼、道谢按聊天处理，不请小模型判断。

**全系统核查。**上游自带的 307 个端到端测试（`scripts/*-e2e.ts`、`*-smoke.ts`）第一次在研究版上跑：154 个通过；没过的 152 个在上游原版上对比，135 个原版也不过（要真实账号、开着的开发版应用或 Mac），17 个原版能过：14 个和自动选择模型有关（见上，修好后剩下的是“自动选模型选了第一个模型”“判断模型的进程被替身算成助手的”这类预期差异），另外是新建助手默认最大权限（预期）、MCP 客户端名（已改）、一条测试的样例文字改名没对齐。开发版本地启动的脚本里 D1 数据库名（`hxbot-auth`）和 `wrangler.jsonc`（`hxbot-account`）对不上，只影响开发环境，需要开发版应用的 27 个端到端测试这里没法跑。

**接进上游的地方。**`hx/quiet.py` 的 quiet_rim、quiet_mouse、quiet_focus、quiet_process_tree、quiet_reads、quiet_stream、quiet_agent_priority、quiet_tabs；`hx/computer_steps.py` 给驱动接线多传 `translate`；`hx/updates.py` 给 Mac 更新传 `userInFront`；`hx/auto_model.py` 给自动选模型的宿主加 `continuing`；`hx/close_upstream.py` 的 MCP 客户端名；`hx/upstream_checks.py` 登记 explorer.exe。新文字 3 条译成 13 种语言（`hx/translations_v170.py`）。

**和方案不一样的地方。**① 原计划的执行器改进（界面变化对比、等待条件、直接赋值输入、按窗口的租约）移到 v1.7.1：这一版只修问题。② 远程桌面的粘贴写主机剪贴板是成员在主机上操作，按设计保留，不放回。

## 28. 并发（一）：多智能体不卡死、团队不设上限、不拒绝只排队（2026-11-17，v1.7.1）

**目的。**用户 2026-11-17：按《需求规格说明书 V2.1》第 5.1 节开发 v1.7.1，“必须无死角穷举式测试，把现在的bug全测出来，并修正！”；“windows同时也要改啊”。需求：BUG-CONC-01（多开智能体卡死：先用可重放的压力脚本复现、找出可证的因果链，再修，修后同一脚本同一机器对照）、CONC-01（桌面端容量闸）、CONC-03（公平排队）、CONC-04（不拒绝只排队）、CONC-10（团队守护 G1～G9）、CONC-12（容量告知）、TEAM-01（团队不设上限）。

**做法。**多智能体并发防拥堵在电脑这一侧解决，不由服务器指挥。HX 自己的代码：

- **容量预算 B**（`src/backend/hx-flow/budget.ts`）：B = (可用内存 − max(2 GiB, 总内存 15%)) ÷ 每回合占用；用电池 ×0.75，温度 serious ×0.5、critical 为 1，处理器降速 < 70% ×0.75，主进程事件循环 p99 > 200 毫秒减 1；限在 2～16。每 5 秒采样，降立刻降，升要连续 3 次。
- **读数**（`src/main/hx-flow-memory.ts`、`hx-flow-readings.ts`，只用 Node）：Linux 读 /proc/meminfo、/proc 下的子进程；macOS 用 vm_stat（空闲 + 非活跃 + 可清除 + 推测页）和内核内存压力等级；Windows 用 os.freemem 和 tasklist（`/FO CSV /NH`，5 秒上限，低于正常优先级，15 秒读一次）。
- **排队顺序**（`hx-flow/order.ts`）：真人消息 → 关键路径 → 团队成员 → 定时任务和后台；每等 120 秒升一档；几个团队按 10 分钟半衰期的近来用量轮流；B ≥ 3 时给真人留一个位置。
- **全机一本账**（`hx-flow/ledger.ts`）：各条线路、团队房间的位置都记在这里；`hasPlace` 决定团队房间里的分派能不能开始。
- **收起闲置进程**（`hx-flow/idle.ts`，G6）：B 被内存卡住且有人在等时，关掉闲了 4 分钟以上、闲得最久的一个团队成员进程。
- **团队**（`src/backend/hx-team/`）：开团不查人数；分派一律接收、进看板排队，回复带排队状态（`withQueueLine`）；限额只认用户在对话里说的（`stated`）；守护 G1～G9 在 `guards.ts`、花费提醒在 `spend.ts`。团队记录的 limits 照写：人数为实际角色数、时间 1440 分钟、交接 1,000,000（旧版本也能打开新记录，验收 TEAM-01-A4）。

## 30. 修问题：程序坞只有一个 HXBot，别的应用存取文件不卡（2026-11-18，v1.7.2）

**目的。**用户 2026-11-18：“继续新版本开发，本次把所有bug都修正了！1、在windows 和mac的程序坞出现多个HXBot的图表！这个一定要修正！2、HXBot启动后，电脑文件打开存储都出先卡死现象！3、其他bug，这次全部处理干净！”。补充：卡的是别的应用里的打开、保存；图标一打开就多个、用着用着变多，Mac 和 Windows 都有。用户在 Mac、Windows 上都不能贴命令结果（“查代码！修正！”），所以原因是查代码找到的，真机上由 GitHub 打包时的 `desktop_check` 检查（《客户端构建》第 6.11 节）。

**查到的原因。**
- 每个“这台电脑上的服务器”是一个 HXBot 子进程（`local-servers.ts`，最多 5 个，原来在 `initialize()` 里同时启动）。上游在子进程启动最早时调一次 `app.dock?.hide()`；这时 macOS 还在激活应用，这次隐藏会被丢掉（Gitify #3100 同样的竞争），图标整场留着，还会在启动时抢一次焦点。
- Windows 上主进程用 Node 起的子进程没写 `windowsHide` 时会开一个命令行窗口（任务栏多一个图标，抢焦点）。
- 上次没正常退出时，留下的服务器子进程还在（父进程已不在），图标和内存都还占着。
- v1.7.1 的容量 B 每个进程各算各的：子进程没有 `hostMemory`，各自建一个 `HxDesktopMemory`，桌面端加 5 个服务器合起来最多 6×B，内存占满、换页，别的应用的打开、保存窗口出不来。

**做法。**
- `src/main/hx-dock.ts`：`hxKeepOutOfDock(app)` 先 `setActivationPolicy("accessory")` 再 `dock.hide()`，`whenReady` 后再做一次，之后在 0.25、1、2.5、5、10、20、30 秒复查，`dock.isVisible()` 时再藏（计时器 `unref`）。`hxKeepChildWindowsHidden(app)`：服务器子进程新建的每个窗口 `setSkipTaskbar(true)`，`show` 时 `hide()`。
- `src/main/hx-child-windows.ts`：只在 Windows 上，把 `node:child_process` 的 spawn、spawnSync、execFile、execFileSync、exec、execSync、fork 包一层，调用方没写 `windowsHide` 时补 `true`（写了的照用），保留 `promisify.custom`；`hx-defaults.ts` 里包好后 `syncBuiltinESMExports()`，让主包 ESM 的具名导入也拿到包过的函数。要显示窗口的三处写明 `windowsHide: false`：`external-link-opener.ts`（用户选的浏览器）、`hx-check` 里打开的记事本和资源管理器。
- `src/main/hx-local-servers.ts`：启动时（后台，不等）用 `ps -axww -o pid=,ppid=,command=`（Mac）或 `Get-CimInstance Win32_Process`（Windows，隐藏窗口）列出命令以这个 HXBot 程序开头、带 `--user-data-dir=<userData>/local-servers/…` 的进程，父进程不在（ppid ≤ 1 或已退出）的发 SIGTERM，5 秒后 SIGKILL。不按进程名找。`hxBackgroundPriority(pid)`：每个服务器子进程启动后设成低于正常的优先级。
- `local-servers.ts` 的 `initialize()` 改为 `Effect.forEach` 一个接一个启动，一个失败只记日志、不挡后面的。
- `src/main/hx-flow-share.ts`：`HxFlowShare` 把本进程正在跑的回合数写进 `appData/HXBot/hx-flow/<pid>.json`（`{running, at}`），`others()` 加上别的活着的进程 20 秒内写过的数，顺手删掉已不在的进程的文件；`hxSharedTurnLimit(B, others) = max(1, B − others)`。`HxDesktopMemory` 每次取样（有活时每 5 秒）写一次、读一次，空闲时写 0，退出时删掉自己的文件。
- 授权记录（需求 AUD-07，规格书原排在 v1.7.9，属于缺陷，这一版先修）：`HxAccessStore.record()` 返回是否写进去；`hxAccessDecide` 先写记录再消耗授权，由“允许一次”或“始终允许”放行的那一步写不进去时，判定改为没有授权、授权不消耗；`hxAccessAnswer` 先写记录，写不进去时回 denied 并说明原因，不加授权、不加规则。
- 团队服务器的命令型 MCP（需求 MKT-04，同上）：`src/main/team-api/hx-mcp-command-servers.ts` 的 `hxRequireAdminForCommandServer(member, transport)`，在 `route-mcp.ts` 的保存、测试（看请求里的配置）和打开（看主机上已存的那一行）前调用，stdio 型要所有者或管理员，用已有的 `requireAdmin`（`error.team.adminRequired`）。Team API 的格式、路由和能力字符串都不变。
- 重跑改造脚本：共用 B 的那一行写在 `hx/flow.py` 的 `application_services` 里（插在 v1.7.1 那一段中间）。写在 `hx/fixes_172.py` 时，重跑 `rebrand.py` 时 flow.py 认不出自己那一段已经改过，会再插一遍，打包时报“重复声明 hxDesktopMemory”。

**接进上游的地方。**`hx/fixes_172.py`（`index.ts`、`local-servers.ts`、`application-services.ts`、`external-link-opener.ts`、`team-api/route-mcp.ts`）和 `hx/flow.py` 的那一行；`rebrand.py` 的 `bug_fixes_172()` 在并发那一步之后。`hx/` 自己的文件（`hx-access/`、`hx-check/`、`hx-flow-memory.ts`、`hx-defaults.ts`）直接改。

**测试。**`src/main/hx-dock.test.ts`、`hx-child-windows.test.ts`（参数位置、调用方自己的 windowsHide、Windows 以外不动、promisify）、`hx-local-servers.test.ts`（Mac、Windows 的进程列表样例：父进程不在才算、别的程序和别的数据目录不算）、`hx-flow-share.test.ts`、`src/backend/hx-access/hx-access-gates.test.ts`（授权记录写不进去：不放行、不消耗、恢复后照常放行一次）、`src/main/team-api/hx-mcp-command-servers.test.ts`。真机：`.github/workflows/hx-build.yml` 的 `desktop-check-mac`、`desktop-check-windows`（`desktop_check = yes` 时），和上一版 0.67.10 对比。
