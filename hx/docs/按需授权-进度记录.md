## 二、已查明的源码事实

### 权限模型（上游）

- `AgentAccess` 只有两个值："full" 和 "workspace"。`DEFAULT_AGENT_ACCESS = "full"`。
- 三档权限 workspace、ask、full 由 access 和 autoApprove 推出：
  - `agentPermissionLevel`：access 是 workspace 时为 workspace；否则 autoApprove 为真时是 full，为假时是 ask。
  - 界面文案：「Workspace only」「Ask first」「Full access」，i18n 键是 `agentSettings.access.*`。
- `DEFAULT_APPROVAL_AUTOMATION_PREFERENCE.defaultAutoApprove = true`，位于 `src/main/approval-automation-store.ts`。所以默认是完全访问、什么都不问。
- 「仅工作区」现在只限制写。读文件、网络、电脑操控（Computer Use）和内置浏览器都不受限。
- `codexSandboxPolicy`（`src/backend/agent/workspace-sandbox.ts`）里 `networkAccess: true`。可写目录：工作区、共享文件夹、用户添加的文件夹、临时目录。
- 每个服务商的工作区限制方式（`workspaceEnforcement`）：
  - Codex：command-sandbox，每轮发送 workspace-write sandboxPolicy。
  - Claude：tool-sandbox，用 PreToolUse 钩子加 Bash 沙箱（`claude-workspace-sandbox.ts`）。
  - 其余 16 家（Grok、OpenCode、Antigravity、Cursor、Cline、Kimi、Devin、Copilot、Mistral、Pi、Muse、Inception、DeepSeek、OpenRouter、Hermes、自定义 ACP）：confined-process，只靠 macOS seatbelt 限制写。`confineSpawnTarget` 在非 macOS 上会抛错，所以这些代理在 Windows 和 Linux 上开「仅工作区」就启动不了。

### 审批和提问（AttentionRegistry，`src/backend/agent/attention-registry.ts`）

- **所有服务商的审批最终都进入同一个入口 `surfaceApproval(client, request, kind)`**（约第 968 行）：
  - `#answerWithoutAsking` 在 `#answersForAgent` 成立时自动同意，条件是「没有工作区沙箱且 autoApprove 为真」。
  - `approvalReply(method, params, decision, rejection)`（约第 2260 行）负责拼出服务商要的回复格式。
- 内置工具的审批走 `awaitToolApproval(client, request, approval, {alwaysAsk, ownerOnly})`（约第 1006 行）。
- 提问类入口：
  - `surfaceDynamicPrompt`（约第 1552 行）：处理 ask_user 工具。回复由 `dynamicPromptResult(answers)` 生成，内容是所选选项的 label。
  - `surfaceUiBlock`：处理 ask_ui 和 request_api_key。
- 谁来回答：
  - `respondToPrompt(input, responder)` 里 `PromptResponder` 只有 privileged（所有者或管理员）。要加一个 owner 标记，让授权卡片只有所有者能答。
  - Team API（`route-agents.ts`）：提问的 privileged = 角色不是 member；审批的 owner = 角色是 owner。
- **安全坑：本机脚本能回答提问。** `respondToLocalAttention` 会调 `respondToPrompt` 且不带 responder（等于按本机用户处理），只有 `localQuestionNeedsHxBot` 判定的问题例外。代理可以自己运行本地脚本，所以授权卡片必须标记成 requiresHxBot，不能让本机脚本代答。
- 回合结束时调用 `clearForTurn(threadId, turnId)`（约第 1814 行）。授权到期收回就挂在这里。
- 提问在 web 端和手机端也会显示：
  - `AgentPromptQuestion` 字段：id、header、question（Markdown）、detail（只在本机显示）、isSecret、options、multiSelect。
  - 跳过回答的结果是 skipped。
  - 手机端 `apps/mobile/.../chat-question-prompt.tsx` **不支持多选**，要补上。
  - 共享组件 QuestionPromptBubble（packages/ui）支持多选、跳过和 Markdown。
- 本地化：
  - 后端写英文源文本（`sourceText`），界面用 `localizeSourceText` 按模板翻译。
  - **但提问卡片和 UI 块不做源文本本地化**，只有审批的 reason 会翻译。
  - 所以授权卡片按主机界面语言直接生成文字，主机语言在 `src/main/language-service.ts`。翻译器用 `sourceTranslateFor(locale)`，或者 HX 自带的字典。

### 工具路由（`src/backend/agent/hxbot-tool-router.ts`）

- hxbot 命名空间：
  - ask_user 在第 601 行进入 `surfaceDynamicPrompt`。
  - capture_screen 和 list_capture_sources 在约第 621 行处理；capture_screen 本身也调用 `awaitToolApproval`（约第 1599 行）。
  - API 密钥工具走 `#apiKeyTool`（约第 736 行），它用 `apiKeyFormSpec` 加 `surfaceUiBlock`。
  - attach_files_to_response 和 web_search 在约第 640 到 680 行。
- hxbot_browser 命名空间的工具全部经过 `this.#browser.handleDynamicTool`（约第 570 行）。这里统一加网站授权检查。
- 直接可用的工具名在 `src/backend/agent/tool-catalog.ts` 的 DIRECT_NAMES 里；工具定义在 `src/backend/hxbot-tools.ts` 的 HXBOT_TOOL_DEFINITIONS 里。

### ACP（`src/backend/acp-client.ts` 第 3219 行 `#requestPermission`）

- `toolCall.kind` 的映射：execute → command；edit、delete、move → file-change；其余 → permissions。
- 目前只传了 kind 和 title。toolCall 里还有 locations（路径）和 rawInput 可用。
- 选项只会选 allow_once 或 reject_once，从不选「永远允许」。
- ACP 的 fs 能力是关闭的（`fs.readTextFile: false`），代理自己读文件，不经过 HX。
- OpenCode 可以通过 `OPENCODE_CONFIG_CONTENT` 设 `"*": "ask"`，让它什么都先问。注意：不要禁用 bash 和 read，免费版需要它们。

### Codex 0.160.1（源码已稀疏克隆到 /tmp/codex-src，会话结束会丢失）

- 审批策略 approvalPolicy 为 "untrusted" 时，**每条命令和每次 apply_patch 都会请求审批**，除非 exec-policy 规则明确放行（`exec_policy.rs` 的 `render_decision_for_unmatched_command`）。
- **重要缺口**：在 untrusted 下，命令一旦被批准、又在沙箱里被拒，Codex 会**不再询问**，直接在沙箱外重跑。代码在 `tools/sandboxing.rs` 的 `should_bypass_approval`，参数 already_approved=true 时就这样处理。
- **补救办法**：只要文件系统策略里有任意一条「拒绝读取」（deny read）条目，就**永远不允许在沙箱外执行**：
  - `unsandboxed_execution_allowed` 返回 false。
  - 申请提权的命令也会退回沙箱内执行（`sandbox_permissions_preserving_denied_reads`）。
  - 每轮发送旧式 sandboxPolicy 时，已有的拒绝条目会保留（`from_legacy_sandbox_policy_preserving_deny_entries`）。
  - 路径匹配规则：最具体的条目优先；深度相同时 Deny 优先于 Write，Write 优先于 Read。
- 限制读取必须用命名的权限配置（permissions profile）。TurnStartParams 的 permissions 字段只能填配置 id，而且不能和 sandboxPolicy 同时用。旧式 readOnlyAccess restricted 已经不支持。
- 命令审批参数里有 command、cwd、reason、command_actions（Read、ListFiles、Search 带路径；其他是 Unknown）和 additional_permissions。
- 文件修改审批参数只有 item_id 等字段，不含路径。路径和操作类型（新增、删除、修改）要按 item_id 从 fileChange 条目里找。
- 回合内追加权限（`item/permissions/requestApproval`，request_permissions 工具）是功能开关项，HX 目前没有打开。

## 三、设计草案（待定稿）

### 1. 档位

- 「仅工作区」改名为**「按需授权」**，存储值仍是 access=workspace，并且 autoApprove=false。15 种界面语言都要改文案。
- 新代理默认用按需授权：`DEFAULT_AGENT_ACCESS` 改为 workspace，`defaultAutoApprove` 改为 false。
- 现有代理做一次性迁移：不改数据库结构，通过设置接口修改，再写一个标记文件防止重复迁移。
- 「先询问」保留。「完全访问」必须手动选，要二次确认，沿用现有确认框，可能再加一层。

### 2. 授权申请工具（所有服务商都能用的直接工具）

**request_access**，参数：

- `reason`：为什么需要。
- `purpose`：用来做什么。
- `targets`：要访问的对象，类型是 folder、file、website、command、screen、search 之一，带一个值。
- `actions`：read、write、delete 的子集。

卡片的显示和回答：

- 以多选提问卡片显示：代理名、原因、目的、目标清单，再让用户勾选允许的行为（读、写、删除）。
- 跳过等于拒绝。
- 只有所有者能回答，本机脚本不能代答。

**release_access**：代理用完后提前释放某一条授权，或全部释放。

### 3. 授权记录

- 按代理、会话、回合分别保存在内存里。
- 收回时机：
  - 回合结束（`clearForTurn` 或回合完成时）。
  - 代理主动调 release_access。
  - 用户在桌面端代理设置里手动「收回」（要新增 IPC 接口）。
  - 用户在任意端按「停止」，回合结束，授权随之全部收回。
- 授权和收回都在聊天记录里留一条说明。

### 4. 拦截判定

总规则：

- 工作区内读和写放行，删除要有 delete 授权。
- 工作区外的读、写、删除，都要有对应路径的授权。
- 命令要有 command 授权，范围是本回合，按命令前缀匹配，卡片列出具体命令。
- 内置的只读命令放行，前提是路径在工作区内（例如 ls、cat、grep、rg、git status/log/diff，以及 Codex command_actions 识别为 Read、ListFiles、Search 的命令）。
- 删除类命令另外要 delete 授权，按经验规则识别：rm、rmdir、unlink、del、rd、Remove-Item、git clean、git rm、find -delete、shred 等。
- 识别不了的服务商请求，退回现有审批卡片，由用户逐项决定。

分渠道：

| 渠道 | 拦截方式 |
|---|---|
| 服务商审批入口 `surfaceApproval` | 按需授权模式下按授权自动同意或拒绝。拒绝时告诉代理先调 request_access |
| Codex | 按需授权模式下 approvalPolicy 改为 "untrusted"。跟踪 fileChange 条目以识别删除；用 command_actions 识别只读命令。见下面的待决问题 |
| Claude | PreToolUse 钩子覆盖所有工具：Read、Glob、Grep 看路径；Write、Edit 是写；Bash 要 command 授权；WebFetch、WebSearch 要网站或搜索授权。钩子把判定转发到同一个入口 |
| ACP | 审批参数补充 locations、toolKind 和 rawInput。OpenCode 在此模式下设成全部先问 |
| 内置浏览器 | 只读动作要网站读取授权：open、navigate、snapshot、screenshot、list_tabs、status、wait_for、hover、scroll。操作动作要网站写入授权：click、type、fill_fields、press、select_option、set_checked、drag、upload_files（还要文件读取授权）、handle_dialog、evaluate、run_script、act、close_tab |
| capture_screen | 要屏幕读取授权 |
| attach_files_to_response | 工作区外的文件要读取授权 |
| web_search | 要搜索授权 |
| Computer Use（电脑操控） | 按需授权模式下不提供，因为 cua-driver 的动作分流层分不清是哪个代理 |
| 非 macOS 上的 confined-process 服务商 | 不再拒绝启动，改为不加沙箱启动，靠服务商的逐项询问加 HX 拦截 |

### 5. 待决问题：Codex 方案

- **方案 A**：untrusted 加 workspace-write。
  - 好处：工作区外写入授权能生效（批准后先在沙箱里试，被拒再到沙箱外重跑）。
  - 缺口：已批准的命令被沙箱拦下后，会不经询问在沙箱外重跑。
  - 对策：命令授权按具体命令前缀给，卡片写明会运行哪些命令。
- **方案 B**：方案 A 再在会话的权限配置里加 deny-read 条目（例如 `~/.ssh`、`~/.aws`、`~/.gnupg`、钥匙串、浏览器配置目录）。
  - 好处：永远不在沙箱外执行，敏感目录读不到。
  - 代价：工作区外写入在当前回合无法生效。
  - 前提：需要用真实 codex 0.160.1 二进制验证配置写法（可以 npm 安装 @openai/codex@0.160.1，用 `codex sandbox` 试）。

### 6. 实现方式

- HX 自有代码放在 `src/backend/hx-access/`，计划这些文件：
  - policy.ts：判定规则。
  - grants.ts：授权记录。
  - commands.ts：命令解析。
  - operations.ts：把各渠道请求映射成操作。
  - card.ts：生成授权卡片。
  - tool.ts：两个工具的定义和处理。
  - messages.ts：多语言文字。
- 每个文件都配 vitest 单元测试。
- 对上游文件的改动写进新的重放步骤 `hx/access_control.py`，用 replace()，新文字已存在就跳过；HX 自有文件加进重放复制清单。
- 还要改：
  - 界面：代理设置里显示当前授权并能收回；改档位文案；手机端提问支持多选。
  - 代理系统说明：讲清按需授权规则和 request_access 用法（developer-instructions.ts、prompts.ts）。
- 测试：
  - 单元测试；typecheck node、renderer、api、mobile 全部通过。
  - 从 e874c72 重放后结果一致。
  - 本地运行检查。
  - 更新文档：指南第 5 节和第 8 节，重新生成页面。
  - 提交、打包、交付。
- 必须告诉用户：真实服务商的端到端测试要在用户自己的 Mac 或 Windows 上、登录账号后进行。

### 7. 已知限制（交付时要说明）

- 已批准的命令本身是程序，内部脚本做了什么（比如 python 脚本里删文件）HX 看不到。
- 部分 ACP 代理的内置读文件工具不会询问，这类读取无法拦截。macOS 上这些代理的写入仍受 seatbelt 限制。
- 网站上的「删除」只能靠代理自己声明，HX 分辨不出删除按钮和普通按钮。
