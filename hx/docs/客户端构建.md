**这一版要打哪几个包：**

| 客户端 | 要不要打 |
| --- | --- |
| Mac、Windows | **要打**（0.67.10） |
| 安卓、iPhone | 下载中心里已经有 v1.6.2 时上传的 1.5.0，就**不用打**；还没有（服务器还没上线过 v1.6.2，下载中心里安卓还是 1.4.9 或更早），就要打，用这一版的源码打出来的同样是 1.5.0 |

下载中心里有没有 1.5.0：登录 https://bot.hxallai.com ，看下载页上安卓那一项的版本号。

**这一版在 GitHub 上打包：只做第 1 节（拿到源码）和第 6 节（在 GitHub 上打包、下载、上传）就够了。**第 2～4 节是在自己的 Mac、Windows 电脑上打包的方法，留作备用；其中第 4.2 节（安卓签名为什么必须一直用同一个）在 GitHub 上打包也同样适用。

**打包前要知道的五件事：**

1. **网络：**在自己电脑上打包，要从 GitHub 和 npm 下载 Electron、依赖包和几个运行时（几百 MB），国内网络常常很慢或失败。在 GitHub 上打包（第 6 节）没有这个问题，你的 Mac 只要能把源码推到 GitHub、能把打好的包下载下来。
2. **磁盘：**每台打包的电脑至少留 20 GB 可用空间。
3. **每个版本用一个新的文件夹解压源码，不要解压到旧的源码目录上面**（新旧文件混在一起，打出来的包可能不对）。安卓的签名文件要从上一个版本的源码目录拷过来（第 4.2 节），这一点最重要。
4. **打包第一步会运行 `python3 hx/rebrand.py`：**它应用全部改造，并检查桌面端、手机端和服务器的全部代码，只要还有指向上游项目的地址或文字就报错停下，不会打出带上游入口的安装包。
5. **发布用的 Mac 版只在 GitHub 上打（v1.6.8 起）：**它用固定证书签名（第 6.3 节第二部分），用户的授权升级后一直有效。在自己 Mac 上打的包（第 2 节）没有固定签名，只能自己试用；上传脚本发现 Mac 版没有固定签名会拒绝上传。

## 1. 拿到源码

### 1.1 核对源码包

交付件放在移动硬盘 US203 上的 `/Volumes/US203/HX Web/2026-11-18/V1.7.1/`。路径里有空格（`HX Web`），命令里要用英文双引号括起来，照下面原样复制即可。在 Mac 终端里：

```bash
cd "/Volumes/US203/HX Web/2026-11-18/V1.7.1"
shasum -a 256 -c SHA256SUMS
```

`hxbot-source-v1.7.1.zip: OK` 才能用。Windows 上：硬盘插到 Windows 电脑后在“此电脑”里看盘符（下面以 `E:` 为例），在 PowerShell 里执行 `Get-FileHash "E:\HX Web\2026-11-18\V1.7.1\hxbot-source-v1.7.1.zip" -Algorithm SHA256`，和 SHA256SUMS 里那一行比对。

### 1.2 解压到一个新文件夹

源码要解压到电脑自己的硬盘上打包，**不要在移动硬盘上直接打包**：移动硬盘常用的 exFAT 格式不支持打包要用到的链接文件和权限，会在“安装依赖”一步出错，速度也慢得多。交付件留在移动硬盘上，从那里解压过来即可。

**Mac：**

```bash
mkdir -p ~/hx/1.7.0
cd ~/hx/1.7.0
unzip "/Volumes/US203/HX Web/2026-11-18/V1.7.1/hxbot-source-v1.7.1.zip"
cd hx-bot
```

以后说的“源码目录”就是 `~/hx/1.7.1/hx-bot`。

**Windows：**路径要短（Windows 对路径长度有限制，放在“桌面”或“下载”里的深层文件夹容易出错）。在 PowerShell 里：

```powershell
mkdir C:\hx\1.7.1
tar -xf "E:\HX Web\2026-11-18\V1.7.1\hxbot-source-v1.7.1.zip" -C C:\hx\1.7.1
cd C:\hx\1.7.1\hx-bot
```

`E:` 换成移动硬盘在这台电脑上的盘符。Windows 读不了这块硬盘时（硬盘是 Mac 格式），先用 U 盘或网盘把 `hxbot-source-v1.7.1.zip` 拷到 Windows 电脑上（例如 `C:\hx\hxbot-source-v1.7.1.zip`），再把上面第二行的路径换成它。

### 1.3 确认版本号

在 Mac 终端里，进入源码目录：

```bash
cd ~/hx/1.7.1/hx-bot
grep -m1 '"version"' package.json
grep -m1 '"version"' apps/mobile/app.json
```

应分别显示 `"version": "0.67.10",` 和 `"version": "1.5.0",`。不是的话，解压的不是这一版的源码。

## 2. Mac 版（在 Apple 芯片的 Mac 上）

必须是 Apple 芯片（M1、M2、M3、M4……）的 Mac。Intel 芯片的 Mac 打出来是 x64 版本，下载中心不认。看芯片：左上角苹果菜单 → 关于本机 → “芯片”一行写着 Apple M…。

### 2.1 一次性准备

打开“终端”，逐行执行：

```bash
xcode-select --install                                     # Xcode 命令行工具（已装过会提示 already installed，跳过）
curl -fsSL https://bun.com/install | bash -s "bun-v1.4.2"  # Bun 1.4.2
```

装完 Bun 后**关掉终端再重新打开**。

Node.js 24：在浏览器打开 https://nodejs.org/dist/latest-v24.x/ ，下载文件名以 `.pkg` 结尾的那一个，双击安装（已经在用 nvm 的，`nvm install 24 && nvm use 24` 也可以）。

**检查准备好了没有**（重开终端后）：

```bash
xcode-select -p        # 显示 /Library/Developer/CommandLineTools 或 /Applications/Xcode.app/...
bun --version          # 1.4.2
node -v                # v24 开头
python3 --version      # Python 3 开头
git --version          # git version 开头
```

### 2.2 打包

```bash
cd ~/hx/1.7.1/hx-bot
bash hx/scripts/build-mac.sh
```

**这样打出来的包没有固定签名，只能在这台 Mac 上试用，不要上传**（macOS 把它当成另一个应用，授权要另给；上传脚本也会拒绝）。发布用的 Mac 版在 GitHub 上打（第 6 节）。

**用 `build-mac.sh`，不要直接运行 `bun run dist:mac`。**刚解压的源码还没有安装依赖，直接运行 `bun run dist:mac` 会报错；`build-mac.sh` 会先做改造检查（确认没有指向上游的地址），再安装依赖（`bun install --frozen-lockfile`），然后才调用 `bun run dist:mac` 打包，最后列出产物和校验值。

屏幕上依次出现 `1/4 应用 HXBot 改造……`、`2/4 安装依赖（会下载 Electron）……`、`3/4 构建并打包（约 10～20 分钟）……`、`4/4 产物：`。成功时最后一段类似：

```
4/4 产物：
-rw-r--r--  1 你  staff   190M  dist/HXBot-0.67.10-arm64.dmg
-rw-r--r--  1 你  staff   185M  dist/HXBot-0.67.10-arm64.zip
-rw-r--r--  1 你  staff   560B  dist/latest-mac.yml
3f5a…（64 位校验值）  dist/HXBot-0.67.10-arm64.dmg

本机试用：打开 dmg，把 HXBot 拖进“应用程序”。
这个包没有固定签名，只能自己试用，不要上传（上传脚本会拒绝）。发布用 GitHub 上打的包（《客户端构建》第 6 节）。
```

打包时还会出现一行提示 `HXBot: this Mac build has no fixed signature ……`，说的是同一件事。中途报错停下时，屏幕上最后几行就是原因，常见的见第 7 节。

### 2.3 打出来的文件

```bash
ls -l dist/HXBot-0.67.10-arm64.dmg dist/HXBot-0.67.10-arm64.zip dist/HXBot-0.67.10-arm64.zip.blockmap dist/latest-mac.yml
head -1 dist/latest-mac.yml      # 应显示 version: 0.67.10
```

| 文件 | 是什么 |
| --- | --- |
| `HXBot-0.67.10-arm64.dmg` | 安装包，用户在下载页下载 |
| `HXBot-0.67.10-arm64.zip`、`.zip.blockmap` | 应用内更新时客户端下载的就是它 |
| `latest-mac.yml` | 写着最新版本号和校验值，客户端靠它知道有新版本 |

**这四个文件都不要删、不要改名、不要挪出 dist**，上传时一起传（上传脚本会自动带上）。

### 2.4 本机试用

双击 `dist/HXBot-0.67.10-arm64.dmg`，把 HXBot 拖进“应用程序”（已经装着旧版本的，选“替换”，数据都在）。研究版没有做苹果的公证，第一次打开会提示“无法验证开发者”，二选一：

- 点“完成”，打开“系统设置 → 隐私与安全性”，拉到最下面点“仍要打开”，输入密码，再点“打开”（macOS 15 起右键“打开”已经不行）
- 或在终端执行 `xattr -dr com.apple.quarantine "/Applications/HXBot.app"`

这台 Mac 以前给 GitHub 打的 HXBot 授过权时，自己打的这个包要另外授权一次（签名不一样）；之后再装回 GitHub 打的包，原来的授权照样有效。

打开后在“设置 → 关于”（设置窗口左侧最下面）里能看到版本 0.67.10。0.67.10 能登录现在的服务器，可以先试。服务器升级到 v1.7.1 以后，0.67.1～0.67.9 照常能登录（v1.7.1 起服务器不再按版本拒绝），它们会自动下载 0.67.10，在弹出的窗口里点“立即更新”或“以后再说”。

## 3. Windows 版（在 Windows 10/11 电脑上）

**Windows 版只能在 Windows 电脑上打包，不能在 Linux 或 Mac 上用 Wine 交叉编译。**打包时有两类东西按“正在打包的这台电脑的系统”来取：

- 语音识别和朗读用的运行时：打包脚本取的是当前系统的版本。
- Claude 智能体等组件的平台专用部分：安装依赖时只装当前系统的那一份。

在 Linux 上交叉编译，打出来的 Windows 安装包里装的是 Linux 的这些组件。安装后能打开、能登录，但语音、Claude 智能体等功能用不了，而且打包时不会报错，很难发现。没有 Windows 电脑时，可以借一台 Windows 10/11 的电脑按本节打包；或者用第 6 节的 GitHub Actions，它用的是 GitHub 的 Windows 机器。

### 3.1 一次性准备

1. **Git for Windows**：https://git-scm.com/download/win ，安装时一路默认。它自带 **Git Bash**，上传安装包时要用。
2. **Python 3**：https://www.python.org/downloads/ ，安装第一页**一定勾选“Add python.exe to PATH”**。
3. **Node.js 24**：https://nodejs.org ，下载 24 开头的 LTS 版安装。
4. **Bun 1.4.2**：打开 PowerShell，执行：

```powershell
iex "& {$(irm https://bun.com/install.ps1)} -Version 1.4.2"
```

全部装完后**关掉 PowerShell 重新打开**，检查：

```powershell
git --version        # git version 开头
python --version     # Python 3 开头。如果弹出了微软商店，说明第 2 步没勾 Add to PATH，重装 Python 并勾上
node -v              # v24 开头
bun --version        # 1.4.2
```

### 3.2 打包

在 PowerShell 里：

```powershell
cd C:\hx\1.7.1\hx-bot
powershell -ExecutionPolicy Bypass -File hx\scripts\build-windows.ps1
```

依次出现 `1/4 应用 HXBot 改造……` 到 `4/4 产物：dist\HXBot-0.67.10-x64.exe`，成功时最后一段类似：

```
4/4 产物：dist\HXBot-0.67.10-x64.exe
（文件大小和 SHA-256）
应用内更新用的文件：dist\latest.yml、dist\HXBot-0.67.10-x64.exe.blockmap
上传到服务器（在 Git Bash 里，或把 dist 里这三个文件拷到 Mac/Linux 上运行）：
  bash hx/scripts/upload-downloads.sh root@服务器IP dist/HXBot-0.67.10-x64.exe
```

脚本提示里的 `root@服务器IP` 就是 `root@47.119.145.170`，上传见第 3.5 节。中途出现红字 `打包失败`、`安装依赖失败` 等，往上看红字前面的几行，常见的见第 7 节。

### 3.3 打出来的文件

## 4. 安卓版（在 Mac 上）

**安卓要不要打，看下载中心里有没有 1.5.0（本文开头的表）。**从 v1.6.2 起，服务器拒绝 1.5.0 以前的手机端登录（强制更新）。下载中心里已经是 `HXBot-1.5.0-android.apk` 的，这一版不用打；还是 1.4.9 或更早的，要用这一版的源码打出 `HXBot-1.5.0-android.apk`，在升级服务器之前传到下载中心。iPhone 版同样（第 5 节）。

不确定手里的 APK 是哪个版本，在 Mac 终端里查（要先做完下面 4.1 节的准备）。把命令里的路径换成那个 APK：在终端里输入到 `badging ` 为止，再从访达把 APK 拖进终端窗口：

```bash
BT="$(ls -d "$ANDROID_HOME"/build-tools/* | tail -1)"
"$BT/aapt2" dump badging "APK的路径/HXBot-x.x.x-android.apk" | grep -o "versionName='[^']*'"
```

显示 `versionName='1.5.0'` 就能继续用；显示 `1.4.9` 或更早的，按本节重新打包。

### 4.1 一次性准备

1. 安装 Android Studio：https://developer.android.com/studio 。第一次打开按向导装好 SDK（一路 Next）。
2. Android Studio → Settings → Languages & Frameworks → Android SDK：
   - “SDK Platforms”页勾上 Android API 36 和 37；
   - “SDK Tools”页勾上 Android SDK Build-Tools；点 Apply 安装。
3. 在终端里执行下面两行，把环境变量写进 `~/.zshrc`，然后**关掉终端重开**：

```bash
echo 'export ANDROID_HOME="$HOME/Library/Android/sdk"' >> ~/.zshrc
echo 'export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"' >> ~/.zshrc
```

4. 检查：

```bash
ls "$ANDROID_HOME/platforms"                 # 列出 android-36、android-37 等
"$JAVA_HOME/bin/java" -version               # 显示版本号（17 或更新）
bun --version && node -v                     # 1.4.2，v24 开头（同第 2.1 节）
```

### 4.2 签名文件：必须一直用同一个（最重要）

安卓靠签名认“是不是同一个应用”。**换了签名，用户手机上的旧版本就不能覆盖升级**，只能卸载重装，数据会丢。签名文件是源码目录里 `hx/keys/` 下的两个文件：`hxbot-release.jks`（签名）和 `keystore.properties`（密码）。

**以前打过安卓包的（有旧的源码目录）**，打包前先把签名文件拷到新的源码目录：

```bash
cd ~/hx/1.7.1/hx-bot
mkdir -p hx/keys
cp ~/hx/上一版的文件夹/hx-bot/hx/keys/hxbot-release.jks ~/hx/上一版的文件夹/hx-bot/hx/keys/keystore.properties hx/keys/
# 密码文件里记着签名文件的完整路径，改成新位置
sed -i '' "s#^storeFile=.*#storeFile=$PWD/hx/keys/hxbot-release.jks#" hx/keys/keystore.properties
chmod 600 hx/keys/*
grep '^storeFile=' hx/keys/keystore.properties    # 应显示 storeFile=/Users/你/hx/1.7.0/hx-bot/hx/keys/hxbot-release.jks
```

（只看 `storeFile` 这一行。文件里的其他行是密码，不要显示、不要发给别人。）

**第一次打安卓包的**，跳过上面这段，打包脚本会自动生成签名文件，并提示“已生成签名文件 …… 请立即备份 hx/keys 目录”。**马上把 `hx/keys` 整个文件夹备份到安全的地方**（加密 U 盘或公司的密码保管工具），不要放进代码仓库，不要发到聊天工具或邮件里。

### 4.3 打包

```bash
cd ~/hx/1.7.1/hx-bot
bash hx/scripts/build-android.sh
```

依次出现 `1/5 应用 HXBot 改造……` 到 `5/5 产物：`，成功时最后显示 `dist-hx/HXBot-1.5.0-android.apk` 的大小和 SHA-256。第一次构建 Gradle 会下载很多东西，要等得久一些。

### 4.4 核对签名没有变

拿这次打的 APK 和上一版的 APK（例如下载中心里的 `HXBot-1.4.9-android.apk`）比一比。第三行里的路径换成上一版 APK 实际所在的位置：在终端里先输入到 `--print-certs ` 为止，再从访达把那个 APK 拖进终端窗口，路径会自动填好：

```bash
BT="$(ls -d "$ANDROID_HOME"/build-tools/* | tail -1)"
"$BT/apksigner" verify --print-certs dist-hx/HXBot-1.5.0-android.apk | grep 'SHA-256'
"$BT/apksigner" verify --print-certs "上一版APK的路径/HXBot-1.4.9-android.apk" | grep 'SHA-256'
```

两行的 SHA-256 必须**完全一样**。不一样说明用的不是原来的签名文件，**不要上传**，回到第 4.2 节找到原来的签名文件重新打包。

### 4.5 在手机上试装

把 APK 发到一台装着旧版本的安卓手机上（数据线、网盘都可以），点开安装，应该提示“更新”而不是“安装”，装完原来的登录和设置都在。（服务器升级到 v1.6.2 之后，旧的登录会失效一次，要重新登录。）

安卓端的作用是远程连接你的桌面端主机，在手机上查看智能体和对话。推送通知这一版还没有接入，应用在前台时消息正常实时显示。

## 5. iPhone / iPad 版（在 Mac 上）

iOS 应用只能用 Xcode 在 Mac 上打包，并且必须用付费的苹果开发者账号签名。**从注册开发者账号、付年费、拿团队号，到准备 Mac、打包、上传、用户安装和以后发布更新，完整步骤在《部署文档》第 11.2～11.11 节，请照那里一步一步做。**这里只列命令和原理。

### 5.1 命令速查

```bash
bash hx/scripts/build-ios.sh --check                                                    # 检查这台 Mac 还缺什么
HX_APPLE_TEAM_ID=你的团队号 bash hx/scripts/build-ios.sh                                 # 打 TestFlight 用的包（默认）
HX_IOS_EXPORT=release-testing HX_APPLE_TEAM_ID=你的团队号 bash hx/scripts/build-ios.sh   # 打直接安装（Ad Hoc）的包
python3 hx/server/scripts/publish-downloads.py --inspect dist-hx/HXBot-1.5.0-ios.ipa    # 看一个包的版本、构建号、签名、能装到哪些设备
bash hx/scripts/upload-downloads.sh root@47.119.145.170 --ios-url https://testflight.apple.com/join/你的邀请码   # 把 TestFlight 链接发布到下载页
bash hx/scripts/upload-downloads.sh root@47.119.145.170 dist-hx/HXBot-1.5.0-ios.ipa            # 把 Ad Hoc 包发布到下载页
```

产物是 `dist-hx/HXBot-1.5.0-ios.ipa`。两种导出方式的文件名相同、签名不同，不能混用：默认导出的包只能用 Transporter 交给 TestFlight，直接装到手机上会失败；传到下载中心时服务器会识别签名，只把能直接安装的包放上下载页。

### 5.2 打包脚本做了什么

先检查环境（macOS、Xcode 26 或更新、CocoaPods、Bun、Node.js 24、Python、团队号），缺什么一次全部列出来。然后：应用改造（含上游地址扫描）→ 安装依赖 → `expo prebuild` 生成 iOS 工程并安装 CocoaPods 依赖 → `xcodebuild archive` 归档（自动签名）→ `xcodebuild -exportArchive` 导出 ipa，最后显示文件大小、SHA-256、版本、构建号和签名方式。失败时把 xcodebuild 最常见的报错翻译成原因和处理办法，完整输出在 `dist-hx/ios/` 下的 prebuild.log、archive.log、export.log 里。

- **签名**：Xcode 自动签名（`-allowProvisioningUpdates`），证书和描述文件由 Xcode 用登录的开发者账号自动创建。第一次构建时自动登记四个包标识（com.hxallai.bot，以及 .ShareExtension、.NotificationService、.ExpoWidgetsTarget 三个扩展）和应用组 group.com.hxallai.bot。归档用的是开发描述文件，所以开发者账号里要至少登记一台设备。
- **版本号**：取 `apps/mobile/app.json` 的 `version`（这一版 1.5.0）。
- **构建号**：环境变量 `HX_IOS_BUILD`，不设时取打包时的时间（年月日时分）。苹果对同一个版本号的每个构建号只收一次，用时间做构建号就不用人去记。
- **团队号**：环境变量 `HX_APPLE_TEAM_ID`。

### 5.3 下载页怎么处理 iOS

服务器上的 publish-downloads.py 读出 ipa 里的版本、构建号、最低系统版本和描述文件：列出了设备的是 Ad Hoc 或开发签名，可以发布，并生成无线安装清单；没有列出设备的是 App Store / TestFlight 签名，不发布并提示改用 TestFlight 链接。门户页的 iPhone / iPad 卡片按实际发布的内容显示：只有链接时是“在 TestFlight 中安装”；只有 Ad Hoc 包时，在 iPhone / iPad 上是“安装”，在电脑上是“下载 .ipa”；两者都有时 TestFlight 是主按钮。

无线安装的地址是 `https://bot.hxallai.com/ota/32位随机串/manifest.plist`，不校验登录（来取文件的是手机系统的安装程序，不带网页的登录状态）。随机串只写在登录后才能读到的下载列表里，不进访问日志，换安装包时自动更换。

服务器设置了 `HX_APPLE_TEAM_ID`（《部署文档》11.6 节第 9 步）后，iPhone 上点 /join 邀请链接会直接打开 HXBot；不设置时邀请链接用浏览器打开，在应用里点“添加服务器”粘贴链接同样可用。

## 6. 在 GitHub 上打包（这一版用这个方法）

在 GitHub 的云端机器上一次打出 Mac、Windows、安卓三个安装包：Mac 版在 GitHub 的 Mac 上打，Windows 版在 GitHub 的 Windows 上打，安卓版在 GitHub 的 Linux 上打，都是各自正确的系统。你的 Mac 只用来把源码推上去、把打好的包下载下来再传到服务器，不用装 Bun、Node.js、Android Studio。

### 6.1 要准备什么、花不花钱

| 要准备的 | 说明 |
| --- | --- |
| GitHub 账号 | 个人账号或公司组织账号都可以，免费版就行 |
| 一个**私有**仓库 | 6.2 节新建，只用来打包 |
| Mac 上的 git | 第 2.1 节第一行 `xcode-select --install` 装的命令行工具里就有 |
| 安卓签名文件 | 6.3 节第一部分，一次性 |
| Mac 签名证书 | 6.3 节第二部分，一次性（v1.6.8 起），要在 Mac 上装 GitHub CLI |

**费用：**私有仓库每个月有 2,000 分钟免费额度和 500 MB 产物存储。额度按 Linux 分钟算，Windows 用 1 分钟扣 2 分钟，Mac 用 1 分钟扣 10 分钟。打一次三个包大约扣 300～500 分钟（Mac 那一项占大头），每个月可以打 4 次左右。免费账号没有绑付款方式时，额度用完任务就停下，不会扣钱；**不要在 GitHub 的 Billing 里调高花费上限（spending limit）**，保持 0 就不会产生费用。额度每月 1 日重置。

### 6.2 一次性：建仓库，让 Mac 能推送

**1. 新建私有仓库。**登录 https://github.com ，右上角“+” → New repository：

- Owner：选你的账号或公司组织；Repository name：`hx-bot`；
- 选 **Private**；
- **下面三项都不要勾**（Add a README file、.gitignore、license），仓库必须是空的；
- 点 Create repository。

**2. 在 Mac 上记下 GitHub 的账号名**（就是仓库地址 `github.com/账号名/hx-bot` 里的账号名），下面的命令都用它。打开“终端”，把 `你的账号名` 换掉后执行（每次新开终端都要先执行这一行）：

```bash
GH=你的账号名
```

**3. 把 Mac 的 SSH 公钥加到 GitHub。**用《上线操作手册》第 1.3 节生成的那把钥匙。复制公钥：

```bash
pbcopy < ~/.ssh/id_ed25519.pub
```

GitHub 右上角头像 → Settings → SSH and GPG keys → New SSH key：Title 填 `HXBot Mac`，Key 里粘贴（Command+V），点 Add SSH key。

**4. 试一下能不能连上 GitHub：**

```bash
ssh -T git@github.com
```

第一次会问 `Are you sure you want to continue connecting`，输入 `yes`。显示 `Hi 你的账号名! You've successfully authenticated, but GitHub does not provide shell access.` 就对了。

一直没反应、最后 `Operation timed out`：国内网络连 GitHub 的 22 端口常被拦，改走 443 端口，执行下面这段后再试一次：

```bash
cat >> ~/.ssh/config <<'EOF2'
Host github.com
  HostName ssh.github.com
  Port 443
  User git
EOF2
ssh -T git@github.com
```

**5. 产物只保留 1 天。**仓库页面 → Settings → 左边 Actions → General → 往下找到 “Artifact and log retention”，填 `1`，点 Save。打好的包下载后不占免费存储。

### 6.3 一次性：把安卓签名文件和 Mac 签名证书放进 GitHub

**一、安卓签名文件。**安卓用签名认“是不是同一个应用”，以后每个版本都必须用同一个签名文件，见第 4.2 节。先看你手里有没有：

```bash
ls ~/hx/*/hx-bot/hx/keys/hxbot-release.jks 2>/dev/null || echo "没有找到"
```

显示“没有找到”时，再想想以前打安卓包是不是在别的文件夹：在那个源码目录的 `hx/keys/` 里找 `hxbot-release.jks`。

**情况一：有（以前在 Mac 上打过安卓包）。**进入显示的那个 `hx/keys` 所在的源码目录，复制签名文件的内容：

```bash
cd ~/hx/上一版的文件夹/hx-bot          # 换成上面显示的路径里 hx/keys 前面的部分
base64 -i hx/keys/hxbot-release.jks | pbcopy
```

签名密码在 `hx/keys/keystore.properties` 里 `storePassword=` 后面，用“文本编辑”打开这个文件自己看（不要发给任何人）。

**情况二：没有**（以前的安卓包是在 GitHub 上没配签名时打的，或者从来没打过）。在 Mac 上生成一个，以后一直用它：

1. 安装 Java（只为了用它的 `keytool`）：浏览器打开 https://adoptium.net/temurin/releases/ ，Operating System 选 macOS，Architecture 选 aarch64，Package Type 选 JDK，Version 选 21，下载 `.pkg` 双击安装。装完在终端里执行 `keytool -help`，显示用法说明就对了。
2. 生成签名文件（会问两次密码，输入时屏幕不显示；**至少 6 位，记牢，丢了就再也打不出能覆盖升级的安装包**）：

```bash
mkdir -p ~/hx/keys && cd ~/hx/keys
keytool -genkeypair -v -keystore hxbot-release.jks -alias hxbot -keyalg RSA -keysize 4096 -validity 36500 -dname "CN=HXBot Research, O=HX AI, L=Shenzhen, C=CN"
base64 -i hxbot-release.jks | pbcopy
```

3. **立刻备份** `~/hx/keys/hxbot-release.jks` 和密码（例如加密 U 盘 + 公司的密码保管工具），不要放进代码仓库，不要发到聊天工具或邮件里。
4. 注意：手机上已经装着的旧 HXBot 如果不是用这个文件签名的，这一次装 1.5.0 时会提示“与已安装的应用冲突”，要先卸载旧的 HXBot 再安装（手机端只保存登录状态和本机设置，智能体和对话都在电脑上，不会丢）。以后的版本就能直接覆盖升级了。

**两种情况都要做：把签名放进 GitHub。**仓库页面 → Settings → 左边 Secrets and variables → Actions → New repository secret，加两项：

| Name | Secret |
| --- | --- |
| `HXBOT_ANDROID_KEYSTORE_BASE64` | 粘贴（Command+V）刚才复制的一大段文字 |
| `HXBOT_ANDROID_KEYSTORE_PASSWORD` | 签名密码 |

Name 一个字母都不能错。保存后 GitHub 不再显示内容，这是正常的。

**二、Mac 签名证书（v1.6.8 起，一次性，必须做，约 10 分钟）。****2026-11-14 已经做过：证书在打包仓库 `mercywangqiang-tech/hx-bot-build` 里，备份在你 Mac 上的 `~/HXBot-签名证书`，以后不用再做。**换仓库或换电脑时才看下面的步骤。macOS 按应用的签名记“屏幕录制”“辅助功能”“App 管理”这些授权。v1.6.7 及以前的 Mac 版没有固定签名，每一版在 macOS 看来都是新应用，用户每次升级都要重新授权。从这一版起，每一版都用同一张证书签名，授权一次以后一直有效。证书在你的 Mac 上生成一次，直接写进这个仓库的 Secrets，不经过别处；GitHub 打 Mac 版时用它签名，签名身份不对的 Mac 版不出安装包。

要准备的：

| 要准备的 | 说明 |
| --- | --- |
| 一台 Mac | 任何能上网的 Mac 都行（不必是打包的那台），系统自带的“终端”和 openssl 就够了 |
| 6.2 节建好的私有仓库 | 例如 `你的账号名/hx-bot`；你的 GitHub 账号要能改它的设置 |
| GitHub CLI（`gh`） | 用来把证书写进 Secrets。没有装：`brew install gh`（没有 Homebrew 的，到 https://cli.github.com 下载 macOS 的安装包） |
| 脚本 | 源码目录里的 `hx/scripts/mac-signing-cert.sh`（交付件里也单独放了一份 `mac-signing-cert.sh`） |

步骤（在“终端”里）：

1. 登录 GitHub CLI（只第一次）：

```bash
gh auth login
```

依次选 `GitHub.com` → `HTTPS` → `Y` → `Login with a web browser`，按提示在浏览器里输入屏幕上的 8 位代码并授权。再执行 `gh auth status`，显示 `Logged in to github.com account 你的账号名` 就对了。

2. 运行脚本（`你的账号名/hx-bot` 换成 6.2 节的仓库）：

```bash
cd ~/hx/1.7.1/hx-bot
bash hx/scripts/mac-signing-cert.sh 你的账号名/hx-bot
```

脚本生成证书“HXBot Code Signing”（10 年有效），写进仓库的 Secrets `HXBOT_MAC_CERT_P12_BASE64`、`HXBOT_MAC_CERT_PASSWORD`，把证书的 SHA-1 指纹写进仓库变量 `HXBOT_MAC_CERT_SHA1`。证书和密码不显示在屏幕上。中途 macOS 可能问一次是否允许访问钥匙串，点“允许”。成功时最后几行是：

```
完成。
  证书：/Users/你/HXBot-签名证书/hxbot-mac-signing.p12（请备份整个文件夹 /Users/你/HXBot-签名证书 到移动硬盘）
  密码：在“钥匙串访问”的登录钥匙串里，名称“HXBot Mac signing”
  证书指纹 SHA-1：（40 位字母数字）（不是密码，可以告诉开发人员，用来核对）
下一步：在 GitHub 仓库的 Actions 里运行“HXBot build”，Mac 版就会用这张证书签名。
```

3. 核对（应看到两个 Secret 和一个变量）：

```bash
gh secret list --repo 你的账号名/hx-bot      # 有 HXBOT_MAC_CERT_P12_BASE64、HXBOT_MAC_CERT_PASSWORD（还有安卓的两项）
gh variable list --repo 你的账号名/hx-bot    # 有 HXBOT_MAC_CERT_SHA1，值和脚本显示的指纹一样
```

4. **立刻备份**整个 `~/HXBot-签名证书` 文件夹（例如加密 U 盘），密码在“钥匙串访问”里名称“HXBot Mac signing”的那一项。不要放进代码仓库，不要发到聊天工具或邮件里。

**只生成一次。**再运行一次，脚本发现已经有证书就停下，不会生成第二张：新证书等于新应用，所有 Mac 用户的授权都要重给一次。换了打包用的仓库时，把同一张证书写进新仓库：`bash hx/scripts/mac-signing-cert.sh 你的账号名/新仓库名 --upload`。证书丢了（Mac 和备份都没有了）才重新生成，那一版发布前要通知 Mac 用户再授权一次。

| 看到的提示 | 怎么办 |
| --- | --- |
| `要先装 GitHub CLI` | `brew install gh`，再做第 1 步 |
| `要先登录 GitHub CLI` | 做第 1 步 |
| `找不到仓库 ……，或者这个 GitHub 账号没有权限` | 仓库名写错了（格式是 `账号名/仓库名`），或者 `gh` 登录的不是仓库所在的账号：`gh auth status` 看一下 |
| `已经有证书：……不要再生成新的` | 证书已经生成过。只想重新写进 GitHub，用 `--upload` |
| `钥匙串里没有“HXBot Mac signing”的密码` | 用 `--upload` 时在另一台 Mac 上：回到生成证书的那台 Mac 上做 |

以后有了苹果开发者账号，改用 Developer ID 证书（用户第一次打开不再要点“仍要打开”）：见第 10 节。

### 6.4 每个版本：把源码推到 GitHub

用第 1.2 节解压出来的源码目录，一条命令（`你的账号名` 换成 6.2 节第 2 步的 GitHub 账号名）。**v1.6.8 起推到放着 Mac 签名证书的仓库 `mercywangqiang-tech/hx-bot-build`：`bash hx/scripts/push-github.sh mercywangqiang-tech hx-bot-build`**（推到别的仓库，Mac 版会因为没有证书而打不出来）：

```bash
cd ~/hx/1.7.1/hx-bot
bash hx/scripts/push-github.sh 你的账号名
```

脚本做三件事，不改动你的源码目录：

- **只推这一版的文件，不推历史记录。**源码包里的历史记录是截断的，GitHub 不接收（会报 `shallow update not allowed`）。脚本在临时文件夹里取出这一版的全部文件，作为一次提交推上去，提交人写的是 `HXBot build <bot@hxallai.com>`，不带任何个人邮箱。
- **去掉上游项目自带的自动任务。**源码里有十几个上游的自动任务（有的每 5 分钟就运行一次），推上去会很快把免费额度用光。只留三个：HXBot 的打包任务 `hx-build.yml`、电脑操控的真系统检查 `hx-computer-check.yml`（6.8 节），和改造脚本要用到的 `release.yml`（它只在推送版本标签时运行，我们不推标签）。这三个都不会自己运行，推上去不扣额度。
- **用这一版整个替换 GitHub 上的上一版**（强制推送到 main 分支）。这个仓库只用来打包，这是有意的。

这两处去掉的东西只影响 GitHub 上的这一份，打出来的安装包和不去掉时完全一样。

正常的输出：

```
取出提交 xxxxxxxx 的文件（桌面端 0.67.10，手机端 1.5.0）……
去掉了上游的 15 个自动任务，留下：hx-build.yml hx-computer-check.yml release.yml
推到 git@github.com:你的账号名/hx-bot.git（约 25 MB）……
……
 + xxxxxxx...xxxxxxx main -> main (forced update)
完成。打开 https://github.com/你的账号名/hx-bot/actions → HXBot build → Run workflow。
```

第一次推的时候最后是 ` * [new branch]      main -> main`。出错时：

| 提示 | 怎么办 |
| --- | --- |
| `这个文件夹里有改动过的文件` | 源码目录被改过（例如在里面打过包、改过文件）。按第 1.2 节重新解压一份到新的文件夹，在那里执行 |
| `Permission denied (publickey)` | 回到 6.2 节第 3、4 步 |

### 6.8 电脑操控的真系统检查（让 GitHub 自己测）

电脑操控（按名称打开应用和设置页、直接读写设置）用的是 macOS 和 Windows 自己的命令和设置页地址。它们对不对，只有在真的系统上跑过才知道。GitHub 有真的 Mac 和 Windows 机器，有桌面，用完即毁，所以这件事交给 GitHub 做，不用人在电脑前一项一项点。

**它做什么。** 在每台机器上用 HXBot 自己的代码把每个功能真的做一遍，再从另一边核对：

| 组 | 做什么 | 怎么算通过 |
| --- | --- | --- |
| 环境 | 记下系统版本；macOS 上确认脚本可以控制“系统事件”、可以读窗口标题 | 有桌面，有授权 |
| 目录 | 读应用清单，存盘后重新读入，再扫描一次 | 系统自带的应用都在；两次扫描一致 |
| 检索 | 约 30 句说法（“蓝牙设置”“dark mode”“zhongduan”……） | 每句找到的就是预期的那一项 |
| 打开 | 按名称打开 3 个自带应用，打开文件夹、文档、网址；试着打开 .sh、.exe 等 9 种会运行的文件 | 进程真的出现；会运行的文件全部被拒绝 |
| 设置页 | 逐页打开系统设置（macOS 40 页，Windows 57 页），读窗口里显示的是什么，截图 | 显示的就是要的那一页 |
| 读写设置 | 每一项：读 → 原样写回 → 真的改成别的值 → 换一条路再读一次 → 改回 | 每一步都对，最后和开始时一样 |
| 闸门和工具 | 自检之前改设置、运行自检、自检之后再改；不合法的值；安全页面 | 自检前不直接改，自检后直接改成功 |
| 探测 | 只读地试一批以后要新增的设置的读命令 | 不判定，只记录 |

每项设置都会被真的改掉再改回，所以这个检查**只能在 GitHub 的机器上跑，不要在自己的电脑上运行**。用户电脑上“设置 → Computer Use → 运行自检”是另一回事，它不改任何值。

**结果有五种：**通过；失败（整次运行标红）；待看（做成了，但自动核对拿不准，要看截图）；测不了（这台机器没有这个硬件，例如虚拟机没有可调亮度的屏幕；这样的设置仍要在真机上自检）；跳过（前一步没过）。成绩单最后列出“可以标成已验证的设置”：在一个系统的每一台测到它的机器上，读、原样写回、真改、改回全部通过。

**机器（默认 5 台）：**`macos-15`、`macos-26`、`windows-2025`、`windows-2022`、`windows-11-arm`。GitHub 没有中文版系统，没有 Windows 10，机器上没有微信这类第三方应用，这几样仍要在真机上看（《上线操作手册》第 1.6 节）。

**两种跑法：**

| | 放在公开仓库里跑 | 在打包用的私有仓库里跑 |
| --- | --- | --- |
| 花不花额度 | 不花。公开仓库用 GitHub 的标准机器不计费 | 一次约 200 分钟（Mac 机器 1 分钟扣 10 分钟） |
| 放上去的是什么 | 只有打好的检查程序一个文件和一个工作流，不含登录、服务器、文档；产品源码一直是私有的 | 整套源码（本来就在） |
| 怎么开始 | 推送就自动开始 | Actions → “HXBot computer check” → Run workflow；或打包时把 “computer_check” 填成 `yes` |
| 结果在哪 | 运行页面的成绩单和 Artifacts；另外自动存到同一仓库的“分支名-results”分支 | 运行页面的成绩单和 Artifacts（`hxbot-check-all`） |

开发期间每一轮用的是公开仓库这个办法，由维护人员来推、来看结果、来修。自己要跑时：

```bash
# 在装好依赖的源码目录里（需要 Bun，见第 2.1 节）
bash hx/scripts/computer-check-public.sh ~/hx/check main
# ~/hx/check 里是三样东西：hx-computer-check.mjs、.github/workflows/hx-computer-check.yml、README.md
# 把它们作为一次提交推到一个公开仓库的 main 分支，GitHub 就自动开始
```

脚本会先检查准备公开的文件里没有服务器地址、域名、邮箱和密钥，有就停下。

**怎么看结果。** 仓库 → Actions → 点最上面那次运行。页面下方是总成绩单：每台机器一列，每组一行；下面是失败的项、待看的项、测不了的项、用时、可以标成已验证的设置。红色表示有失败的项或有机器没有交回结果。页面最下面的 Artifacts 里，`hxbot-check-all` 是成绩单、全部数据和需要人看的截图，`hxbot-check-机器名` 是那台机器的全部截图（每个设置页一张，每项设置改前改后各一张）。

### 6.9 一步步操作、应用命令和真实模型的检查（让 GitHub 测，v1.6.7 起）

一步步操作应用（第 1.6 节第一部分）要用真的电脑操控驱动在真的桌面上跑，应用命令要在真的 Mac、Windows 上跑，团队协作要用真实模型跑。这些也放在公开仓库里，由 GitHub 的机器测（每一项做完就写到运行页面的日志里，某一段卡住时能看出卡在哪一步；每一段有时限，超时记“失败”并接着跑下一段）：

| 机器 | 做什么 | 怎么算通过 |
| --- | --- | --- |
| `macos-15`、`macos-26`、`windows-2025` | 下载随包的驱动（cua-driver，版本和校验值取自 `native-runtime.lock.json`），像 HXBot 一样启动；打开文本编辑、记事本里的一个文件；按固定步骤在文字框里输入、保存；“删除”这类步骤；按停止键；再让真实模型自己列计划、一步步输入并保存 | 驱动答复；找到窗口、读出文字框；文件里真的有输入的文字；“删除”先停下来问；停止后不再执行；（有模型时）模型先列计划再做，文件里有它输入的文字 |
| `macos-15`、`macos-26`（v1.6.8 起） | 装应用（computer_install）：用 HXBot 自己的代码把一个测试应用的 1.0（.app）、2.0（.zip）、3.0（.dmg）依次装进“应用程序” | 1.0 装上，读回版本和签名，隔离标记保留；装 2.0 时先问、不动原来的；同意后装上 2.0，旧版进废纸篓、不留临时文件；从磁盘映像装 3.0，装好后卸下映像 |
| `macos-15`、`macos-26`、`windows-2025`（v1.6.9 起） | 应用命令和脚本（computer_app、computer_run）：用 HXBot 自己的代码操作文本编辑、记事本：列出运行中的应用、切到前台、窗口放到左半边、读菜单并点“编辑 › 全选”（Mac）、隐藏、正常退出、运行一段 JXA 或 PowerShell 脚本、有没保存的改动时退出、读默认浏览器、改默认应用（Mac：.md 文件改成文本编辑；Windows：打开“默认应用”页） | 每一项见成绩单。结果里写明走的是哪条路（直达、命令）；GitHub 的 Mac 上没有人点“是否允许 HXBot 控制文本编辑”的系统框，用 AppleScript 改文件内容那一项记“提醒”，不算失败；macOS 26 改文件类型的默认应用也弹框确认，那一项也记“提醒” |
| `macos-15`、`macos-26`、`windows-2025`（v1.7.0 起） | 不打扰其他应用（quiet）：读最前面的应用、用户切走后不拉回目标应用、松开卡住的修饰键、后台命令最低优先级、助手的进程低于正常优先级、Windows 上停进程树时留下有窗口的应用、检查前后剪贴板不变（Q1～Q7）；一步步输入时驱动不碰剪贴板（S9），按键保护不误拦（S5） |
| `ubuntu-latest` | 用真实模型走一遍团队协作：建议卡、组队（人数、时长、交接次数按用户的话）、带头的看看板、交接单（检查程序故意删掉第一张的一行，看它被退回后能不能补全）、成员交回结果（检查程序代写）、用户插话（加时间、传话、换人）、交回最终结果、另起一个团队后叫停。团队的代码是 HXBot 自己的，房间和成员干的活是假的 | 每一项见成绩单；模型写得不够好的记“提醒”，不算失败 |

**模型从哪来。**GitHub 的机器上没有可用的免费模型（2026-11-14 实测：OpenCode 的免费模型经它自己的客户端也回答额度已用完；GitHub Models 只回“OK”）。要让真实模型那几项也跑，在公开仓库的 Settings → Secrets and variables → Actions 里加三个 Secret：`HX_CHECK_MODEL_URL`（OpenAI 兼容的地址，例如 `https://api.deepseek.com/v1`）、`HX_CHECK_MODEL_KEY`（密钥，只放在这里，不要发到别处）、`HX_CHECK_MODEL`（模型名，例如 `deepseek-chat`）。没有配时这几项记“跳过”，上线前在真机上补看（《上线操作手册》第 1.6 节第二部分）。检查程序也能经 OpenCode 自己的客户端（`opencode acp`）用它的免费模型（`--opencode <可执行文件>`），但在 GitHub 的机器上额度已用完，所以工作流不下载 OpenCode。

```bash
# 在装好依赖的源码目录里（需要 Bun，见第 2.1 节）
bash hx/scripts/real-check-public.sh ~/hx/real main
# ~/hx/real 里是 hx-real-check.mjs 和 .github/workflows/hx-real-check.yml，放进同一个公开仓库推送即可；
# 只有这两个文件变了才会跑（6.8 节的检查也只在它自己的文件变了时跑）
```

结果在运行页面的成绩单、Artifacts（每台机器的 `report.json`、`summary.md`、`log.txt`：模型每一轮调用了什么、得到什么回答），以及“分支名-results”分支的 `real/<编号>/`。检查程序不连网也能自查：`node hx-real-check.mjs --self-test --out out`（用按剧本回答的模型把协作那一段跑通）。

### 6.10 并发的真系统读数检查（让 GitHub 测，v1.7.1 起）

HXBot 按可用内存算“同时能做几件”（预算 B）。Windows 和 Mac 读内存、读智能体进程的方法和 Linux 不同，要在真的 Windows、Mac 上看一次。这一项也放在公开仓库里，由 GitHub 的机器测，不计费：

| 机器 | 做什么 | 怎么算通过 |
| --- | --- | --- |
| `windows-2025`、`windows-2022`、`windows-11-arm` | 起 2 个各占 150 MB 的测试进程，用 tasklist 读它们的内存；新起一个 PowerShell 要多久（两次），常驻的 PowerShell 就绪要多久、5 次回答各要多久；像智能体那样起一个进程树（一个有窗口的应用、一个没窗口的进程），经常驻 PowerShell 列出要停的进程，停下后看谁还在 | tasklist 读到 2 个、合计 280～800 MB；常驻 PowerShell 就绪、5 次回答都对；要停的进程里有没窗口的那个、没有有窗口的应用；停下后有窗口的应用还开着、其余都停了。耗时写进成绩单 |
| `macos-15`、`macos-26` | 用 vm_stat 估算可用内存，同时读内核的内存压力等级（`kern.memorystatus_vm_pressure_level`）和 `memory_pressure` 的空闲比例，对照记录一次（需求 CONC-01-A4）；起 2 个各占 150 MB 的子进程，用 ps 读它们的内存 | 估算的可用内存大于 0、不超过总内存；ps 读到至少 2 个、合计至少 280 MB。三个数字写进成绩单，作为参数表的依据 |

```bash
# 在装好依赖的源码目录里（需要 Bun，见第 2.1 节）
bash hx/scripts/flow-check-public.sh ~/hx/flow flow-check
# ~/hx/flow 里是 hx-flow-system-check.mjs 和 .github/workflows/hx-flow-check.yml；
# 把它们作为一次提交推到公开仓库的 flow-check 分支，GitHub 就自动开始
```

脚本会先检查准备公开的文件里没有服务器地址、域名、邮箱和密钥，有就停下。结果在运行页面的成绩单和 Artifacts 里（每台机器一个 `report.json`）。

最近一次：2026-11-18（v1.7.1），运行 44248506003，5 台全部通过。读数见《并发根因报告-v1.7.1》第 6 节。

进程树那一项的应用经 `cmd /c start` 打开，和智能体打开应用的方式一样。不要改成用 Node 直接起：Node 把自己直接起的子进程放进“父进程关掉就一起关”的作业对象，停下后应用会被一起关掉，这一项就会误报失败。

## 7. 打包出错了怎么办

| 看到的提示 | 原因 | 怎么办 |
| --- | --- | --- |
| `改造失败，以下位置在上游代码中找不到` 或 `rebrand.py` 报错 | 源码不完整，或解压到了旧源码上面 | 按第 1.2 节重新解压到一个新的空文件夹 |
| `需要 Node.js 24 或更新（当前 v20…）` | Node 版本不对 | 按第 2.1 / 3.1 节装 Node.js 24，重开终端 |
| `缺少 Bun，见脚本开头的准备步骤` / `bun: command not found` | Bun 没装好，或装完没重开终端 | 重开终端；还不行就重新执行装 Bun 的命令 |
| `提示：这台 Mac 不是 Apple 芯片，产物将是 x64 版本` | Intel 芯片的 Mac | 换一台 Apple 芯片的 Mac，或用第 6 节的 GitHub Actions |
| 卡在 `2/4 安装依赖` 很久，或 `ETIMEDOUT`、`ECONNRESET`、`fetch failed` | 访问 GitHub、npm 太慢或不通 | 换网络后重新执行同一条命令（已经下载的部分不会重下），或用 GitHub Actions |
| Windows：`无法加载文件 ……，因为在此系统上禁止运行脚本` | PowerShell 的执行策略 | 命令前面要带 `powershell -ExecutionPolicy Bypass -File`，照第 3.2 节原样复制 |
| Windows：`python` 打开了微软商店，或 `改造失败` 前面提示找不到 python | Python 没加进 PATH | 重新运行 Python 安装程序 → Modify，勾上“Add Python to environment variables” |
| Windows：`EPERM`、`EBUSY`、文件被占用 | 杀毒软件或资源管理器正占着文件 | 关掉打开着 dist 的资源管理器窗口，暂时把源码目录加入杀毒软件的白名单，再执行一次 |
| 安卓：`请先设置 ANDROID_HOME` | 第 4.1 节第 3 步没做或没重开终端 | 做第 4.1 节第 3 步，重开终端 |
| 安卓：`Keystore file … not found` | 拷了签名文件但没改 storeFile 路径 | 执行第 4.2 节的 `sed` 那一行 |
| 安卓：`SDK location not found` 或缺某个 platform | SDK 没装全 | 第 4.1 节第 2 步，在 Android Studio 里装上 |
| GitHub 的 mac 任务：`Mac 版签名不对：仓库里没有登记签名证书（变量 HXBOT_MAC_CERT_SHA1）` | 第 6.3 节第二部分没做，或写进了别的仓库 | 做第 6.3 节第二部分；`gh variable list --repo 你的账号名/hx-bot` 应有 `HXBOT_MAC_CERT_SHA1` |
| GitHub 的 mac 任务：`签名身份不是登记的证书 ……` | 仓库里的证书和登记的指纹不是同一张（例如在另一台 Mac 上又生成了一张） | 用原来那张：在生成它的 Mac 上运行 `bash hx/scripts/mac-signing-cert.sh 你的账号名/hx-bot --upload`。**不要为了让它通过去改登记的指纹**：那等于换了证书，所有 Mac 用户都要重新授权 |
| GitHub 的 mac 任务：`钥匙串里没有可用的签名证书` | Secrets 里的证书或密码不对 | 在生成证书的 Mac 上用 `--upload` 重新写一次 |
| 上传时：`HXBot-…-arm64.dmg 的签名身份不对，没有上传` | 传的是自己 Mac 上打的包（没有固定签名），或混了别的包 | 用 GitHub 上打的 Mac 包（第 6.6 节的 `mac` 文件夹）。只是测试包、确实要传：命令前面加 `HXBOT_ALLOW_UNSIGNED_MAC=1`（升级后 Mac 用户的授权会作废，不要用于发布） |

修好后直接重新执行打包命令即可，不用删源码目录。实在不行，把出错前后 30 行发给维护人员。

## 9. 应用内更新是怎么工作的（了解即可）

客户端只从弘犀服务器取更新，不连上游项目；更新文件只给登录了的客户端。

| 客户端 | 怎么更新 | 用到服务器上的什么 |
| --- | --- | --- |
| Windows | 有新版本时自动下载（只下载有变化的部分），弹出“更新 HXBot”，点“立即更新”重启安装（0.67.1 是下载完 10 秒后自动重启；0.67.2 起 10 分钟内没人点才在空闲时自动安装） | `updates/desktop/latest.yml`、新旧版本的 `.exe.blockmap`、新的 exe |
| Mac | 自动下载新版本的 ZIP，校验后替换“应用程序”里的 HXBot（研究版没有苹果的 Developer ID 签名，用不了系统的更新框架；替换不了时在访达里显示下载好的新版本）。0.67.7 起每一版都用同一张证书签名，升级后授权照样有效；从 0.67.6 及以前升到 0.67.7 的那一次要再授权一次 | `updates/desktop/latest-mac.yml`、`HXBot-版本-arm64.zip` |
| 安卓 | 整屏提示有新版本，点“更新”用系统浏览器下载新的 APK，安装要用户自己点 | `updates/mobile.json`、`/ota/随机串/HXBot.apk` |
| iPhone / iPad | 同上，点“更新”打开无线安装页（Ad Hoc）或 TestFlight | `updates/mobile.json` |

- 桌面端 0.67.0 及以前、手机端 1.4.x 及以前没有应用内更新，要从下载中心下载、安装一次；之后都在应用里更新，数据保留。
- 客户端总是直接更新到服务器上最新的版本，不用一版一版地升，服务器上每个平台只放最新的安装包就够了。
- 每次都要**先上传新客户端，再升级服务器**（v1.6.2～v1.7.0 的服务器会拒绝低于最低版本的客户端）。v1.7.1（0.67.10）起更新不再强制：服务器不按版本拒绝客户端；0.67.10 起，打开 HXBot 时找到的新版本自动下载、装好，在助手都空闲时重启进入新版，不用点（大版本也一样）。还装着 0.67.2～0.67.9 的电脑按它们自己的规则弹窗，版本号第二段一变会挡住界面，所以在这些电脑都装上 0.67.10 之前，新版本的版本号保持 0.67.x。
- **新功能介绍：**每版的新功能写在源码的 `hx/release-notes.json`（中文、英文各 2～4 条），打包时写进 `electron-builder.yml` 的 `releaseInfo`，随 `latest.yml`、`latest-mac.yml` 传到服务器，更新窗口里显示出来。没有写这一版的新功能时改造脚本会报错，不能打包。
